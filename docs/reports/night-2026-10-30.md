## The short version

1. **The safe area now ends at 0xB0000** (your "Yes, raise it"): the 3D
   lists get 104 KiB of the fast memory instead of 96. Code, tests and
   ADR-0034 (amendment P) updated.
2. **Your "take 3 more tests" paid off: there is a better answer than the
   speed switch.** Two findings:
   - **Most of the problem we were curing was something else.** Last
     night's "drawing into slow memory at 143 MHz goes wrong with the
     screen on" (18 of 20 frames) came from the 3D lists sitting in slow
     memory. With the layout we actually ship (lists in fast memory, the
     underlay on), it's one pixel, in about 2 of 100 light frames.
   - **A cure that keeps full speed:** an invisible (fully transparent)
     full-screen layer blended over the frame. It spreads the core's
     writes out, and every frame is right at full divide-1 speed.
3. **It beats the speed switch on every game frame, and changes no clock:**

   | Frame | Invisible layer, 143 / 1 | Speed switch, 143 / 2 |
   |---|---|---|
   | Flat | 8.70 ms | 9.18 ms |
   | Layered | 8.73 ms | 11.28 ms |
   | Textured | 15.30 ms | 15.53 ms |
   | Depth | 8.73 ms | 11.34 ms |

   Up to 23% faster, and the clock rule (ADR-0035 rule 8) needs no
   change for it. It only applies to frames drawn into slow memory (the
   copy path); every other frame is untouched.
4. **Both were soaked an hour each with the screen on, both perfectly
   clean:**
   - the speed switch: 16,572 round trips, 0 wrong, no screen hiccups,
     1 microsecond a switch;
   - the invisible layer: 32,592 frames, 0 wrong, no screen hiccups.
5. **Something we ruled out:** cutting the display's memory reads to a
   quarter changed nothing. The display's reading isn't the lever; the
   pace of the core's own writes is.
