## Ruling 1: ADR-0038, the game path (G1–G6)

**In plain English:** this ADR decides how a game's frames get to the
screen. All three ways (full size, half height with each line shown twice,
quarter size enlarged smoothly) are measured. The driver would pick one
each frame, a game could be locked to one, and two frames would be in
flight at once.

**Recommendation:** adopt G1, G3 and G5 as written. Adopt G2, G4 and G6
with the changes below:

- **G2:** order the ways by measured time, not by pixel count.
- **G4:** a full check of every frame first.
- **G6:** stays held until R20's games hold lifts.

The one finding Reid has not seen yet: on GC2CP's test frames, the
quarter-size way is **slower than full size** on flat frames at 74.75 / 1
(12.4 against 10.2 ms).

**Common evidence:**
- Run: GC2CP low on the X51v, 2026-10-29, `local/rp-gpubench-runGC2CP-low-2.txt`, 256 renders, none hung.
- 2700g.md "GC2CP's pipelined ways at Windows Mobile's clock and 74.75 / 1".
- Times are the fastest frame, in ms, for flat / layered / textured / depth. These are test frames, not games: ADR-0038 says so itself.

| Way | WM 99.67 / 2 | 74.75 / 1 |
|---|---|---|
| (a) native 480 x 640 | 14.3 / 14.9 / 21.3 / 15.1 | 10.2 / 10.6 / 17.8 / 10.7 |
| (b) 480 x 320, serial | 7.3 / 7.7 / 11.2 / 7.7 | 5.2 / 5.5 / 9.7 / 5.5 |
| (e) 480 x 320, two in flight | 6.4 / 6.7 / 10.2 / 6.7 | 4.2 / 4.4 / 8.8 / 4.5 |
| (d') 240 x 320 converted, 2D apart | 14.1 / 14.3 / 16.2 / 14.3 | 12.4 / 12.5 / 15.0 / 12.6 |
| (d) 240 x 320 converted, 2D beside | 11.4 / 11.4 / 13.9 / 11.5 | 11.5 / 11.6 / 14.5 / 11.6 (**16–38 stray words a frame**) |

### G1. Which routes

> ### G1. Which routes
>
> | | A: native only | B: native + 480 x 320 | **C: all three (recommended, and the owner's 2026-10-28 word)** |
> |---|---|---|---|
> | Heavy scenes | stutter | half the pixels | a quarter |
> | Picture | best | blocky down | softest, smooth |
> | Cost to build | none | the doubling switch | the conversion and the scaler set-up |

- **Options:**
  - A: native only.
  - B: native plus 480 x 320.
  - C: all three. This is Reid's word of 2026-10-28, and the ADR records it.
- **Evidence:**
  - Route 2 (480 x 320) is 1.96x faster than native at 74.75 / 1 (flat: 5.2 against 10.2 ms), and 2.08–2.42x with two in flight (table above).
  - Route 3 (240 x 320 smooth 2x, way d') against native at 74.75 / 1:
    - flat frame: 22% slower
    - textured frame: 16% faster
  - Route 3 against native at WM: 1% faster flat, 24% faster textured.
  - Route 3's converter output is exact in its words (R89, GC2CX: 38,400 of 38,400). Its on-screen colour is not judged.
  - Route 3 at 74.75 / 1 has R80's rare single wrong pixels: 0–17 of 250 renders, never textured. At WM: 0 of 2,000.
- **Rule 0:**
  - **Original way:** Dell's driver offers native, or doubling by pixel repeat.
  - **Modern way:** consoles' dynamic resolution, rendering smaller and scaling up.
  - **Ours:** the display's own line doubling (free) and the video plane's scaler (a hardware enlarge, no copy).
  - **What is proven:** route 2's speed and exactness (GC2CT).
  - **Not proven:** that route 3 ever wins on a real game. On the test frames it pays a fixed conversion and 2D cost, which only the textured frame (and the flat one at WM, by 1%) outweighs.
- **Performance:** keeping route 3 costs nothing when unused. It wins only on scenes whose pixel cost exceeds its fixed cost.
- **Correctness risk:**
  - Route 3's colour is unjudged (R89, Reid's eye).
  - R80 at 74.75 / 1.
  - Route 3 must never be chosen where it is slower (that is G2).
- **Reversible:** yes. A route is a driver option, and dropping one later deletes code, not data.
- **Recommendation:** **C, as Reid said.** Route 3 ships only after R89's eye check and the G2 change below. **Not to tick:** "route 3 is faster". It is faster only on textured test frames.
- **Would overturn:** the first game port measuring route 3 slower than route 2 on every one of its scenes. Then route 3 adds code for no frame anyone would use, and B wins.

### G2. Choosing per frame (dynamic resolution)

> ### G2. Choosing per frame (dynamic resolution)
>
> | | A: the game picks once | **B: the driver picks per frame from the last frames' times (recommended)** | C: per frame from a prediction of this frame |
> |---|---|---|---|
> | How | fixed at start | step down when the mean of the last 8 frames passes the frame budget (33.3 ms at 30 fps, R/port-fps rule), step up only after 60 frames well under it (hysteresis: no flicker between routes) | needs the scene's cost before drawing it |
> | Switch | never | in the blanking, at a frame boundary (the planes' registers latched) | same |
> | Risk | stutter | one route change seen (the picture's sharpness) | mispredictions |
>
> Rule 0: consoles' dynamic resolution (PS4/Xbox One era) scales the render
> target per frame from GPU time; ours does it with the display's own
> doubling and scaler, so the step costs no copy.

- **Options:** A (fixed), B (from recent times), C (predicted).
- **Evidence:**
  - The routes' costs are in the table.
  - **Nothing measures a route switch.** There is no run of switching in the blanking. The 8 / 60-frame thresholds are first drafts, not fitted.
  - The ordering problem: B's "step down" assumes native → 480 x 320 → 240 x 320 gets cheaper. At 74.75 / 1 the last step goes **up** on flat frames (5.2 → 12.4 ms).
- **Rule 0:**
  - **Original way:** a fixed resolution.
  - **Modern way:** consoles' dynamic resolution scaling.
  - **Why ours could win:** the switch costs no copy.
  - **Rule 0 also says:** the 8- and 60-frame constants, and a "native → half → quarter" ladder, are copied defaults until fitted to this hardware.
- **Performance:** B can only gain if each step down is really cheaper. The driver should **rank the routes by their own last measured times for this game**, not by pixel count.
- **Correctness risk:** a half-switched frame (planes latched mid-frame) shows as a one-frame glitch, and it is not measured.
- **Reversible:** yes. It is a policy in the driver, and A is B held to one route.
- **Recommendation:** **B, with three changes:**
  1. Rank routes by measured time, per game, not by pixel count.
  2. Treat the 8 / 60 thresholds as provisional, to be fitted on the first game port.
  3. Tick nothing until a device run switches routes every N frames and checks that every frame is whole (a hash per frame, 0 torn or half-switched).
- **Would overturn:**
  - That switch run showing glitches that latching in the blanking cannot remove. Then A, or switching only at scene loads.
  - The first game port showing frame times that vary so little that switching never fires. Then B is cost without gain, and A is simpler at equal speed.

### G3. A per-game override

> ### G3. A per-game override
>
> **Recommended:** the user can hold a game to one route (or to "automatic")
> in the game's settings, remembered per game; the default is automatic. A
> game's own request (a fixed-resolution old title) is honoured.

- **Options:** an override (as written), or none.
- **Evidence:** none needed for speed. This is a settings field.
- **Rule 0:** the original way is a per-app fixed mode. Ours is the same field on top of the automatic choice, so there is nothing to beat.
- **Performance:** none.
- **Correctness risk:** a user who forces native on a heavy game gets stutter they chose. Old fixed-resolution titles keep working (the legacy rule).
- **Reversible:** yes.
- **Recommendation:** **adopt as written.**
- **Would overturn:** nothing measurable. Only Reid's taste on the settings screen, which the shell's design decides.

### G4. Two frames in flight

> ### G4. Two frames in flight
>
> **Recommended:** for routes 2 and 3, the CPU builds frame N + 1 while the
> GPU draws N (`prepare` / `start_prepared`), the 2D placements of the UYVY
> route kept apart from the render (d', no stray words). Native stays one
> frame (its set-up is already overlapped by the GPU's poll). **To prove

> both clocks; (e) 0 words off on each frame's last picture at both; (d),
> the 2D placed beside the render, 0 at WM clock and 16-38 a frame at 74.75
> / 1. Two in flight against one at a time at 480 x 320: 12-14% less a
> frame at WM clock, 15-19% at 74.75 / 1. A result for the vote, not a
> ruling.

- **Options:**
  - Two in flight for routes 2 and 3 (as written).
  - Two in flight for route 2 only.
  - One frame everywhere.
  - Route 3 with 2D beside the render, way (d).
- **Evidence:** GC2CP low. CPU set-up is 0.85–0.94 ms a frame; waiting on the core is 3.6–13.1 ms, so the core sets the pace.

  | Measure | Result |
  |---|---|
  | (e) against (b), WM 99.67 / 2 | **12–14% less** (flat: 6.4 against 7.3 ms) |
  | (e) against (b), 74.75 / 1 | **15–19% less** (flat: 4.2 against 5.2 ms) |
  | (e) stray words | 0, **checked on each test's last picture only** |
  | (d') stray words | 0 at both clocks, every frame checked against its serial result |
  | (d) stray words | 16–38 a frame at 74.75 / 1 (R30) |
  | (d) against (d') | (d) is 3–19% faster but **wrong**, so it is out |

- **Rule 0:**
  - **Original way:** Dell's GLES driver: serial submits.
  - **Modern way:** the CPU builds frame N + 1 while the GPU draws frame N, as every modern driver does.
  - **Why ours wins:** measured 12–19% less a frame on route 2.
  - **Gap to close:** (e) was checked on its last picture only. Under rule 0 that is not proof every frame is right.
- **Performance:** route 2 gains 0.9–1.0 ms a frame (flat). Route 3's (d') is the only clean form, but tonight's run has no serial route-3 time to compare it against. Its gain over serial is unmeasured at these clocks, so make no claim.
- **Correctness risk:**
  - (e)'s unchecked frames.
  - (d) is a proven fault, R30.
- **Reversible:** yes. `prepare` / `start_prepared` against `start` is a driver path, and one-at-a-time stays available.
- **Recommendation:** **two in flight for route 2 now**, ticked only after one device run that hashes **every** (e) frame against its serial result (0 off). **Done 2026-10-29: 800 of 800 right** (see "Device runs since"). It is a count over those frames at WM and 74.75 / 1, not proof of zero, and the test frames are not a game. **Route 3 uses (d') only, never (d).** Route 3's in-flight gain is to be measured against a serial run in the same image before it is claimed.
- **Would overturn:**
  - Any (e) frame wrong in the every-frame run. Then route 2 goes serial until found, at a cost of 0.9–1.0 ms a frame (15–19%).
  - R30's overlap fault being fixed. Then (d)'s 3–19% over (d') is worth re-measuring.

>

> ### G6. Tearing
>
> **Recommended:** the game path follows R20's ruling once GC2CA's picture
> is judged: C (render behind the scan, top-down order) where the route's
> tile order allows; the checkerboard order (divide 1's cure) takes A's copy

## Ruling 2: C71, what the second screen becomes

**In plain English:** the fix for the stale pixels is proven: put the
visible screen at the start of graphics memory. Only one 600 KiB screen
fits in the safe 696 KiB, so the second screen needs a job:

- **R-A:** delete it. +600 KiB, but 2D drawing tears.
- **R-B:** keep it outside as 2D's back picture. 2D stays tear-free, at the cost of one copy in 3D frames.
- **R-C:** the old off-screen 3D way. It breaks at divide 1 above 74.75.

**Recommendation:** R-B now, with R-A as a later upgrade once R20's
scheduler is proven on 2D frames.

**Options and evidence** (`docs/design/c71-screen-place.md`; the overnight
report, section 12):

| | R-A one screen | R-B 2D back picture | R-C amendment P's A |
|---|---|---|---|
| Cure for C71 | yes | yes | yes |
| Memory | +600 KiB to the pool | none freed | none freed |
| 2D frames | draw into the visible picture, so they **tear** | today's tear-free flip | tear-free |
| 3D frames | R20 can schedule them (120 of 120 tear-free) | the same, plus copying 2D's changed rectangles in | drawn off screen, then a copy |
| Added cost | none | 2D copy into screen 0, up to ~5 ms whole-screen (G20), in proportion to the changed area, 3D frames only | a whole-screen copy every 3D frame |
| Conflicts | none | none | **contradicts P1 = C; fails at divide 1 above 74.75 (G21)**; works only if amendment D ends at divide 2 (held) |

**Measured facts:**
- C71 runs: 1–20 of 20 renders differ with the screen at `0x9D6000`.
- With the screen at `0x0`: **0 of 100**, each render ~2 ms faster.
- GC2S: 9 of 9 kinds right at 133.25 and 149.50 / 2, and **4–5% faster**.
- G18 / G19: right while the screen ends by `0xAE000`.
- G20: the 2D engine is unaffected by where the display reads.
- R20 covers 3D frames only. **Covering 2D frames is not built or measured.**

**Rule 0:**
- **Original way:** Dell and WM keep one screen at `0x0`, no flip (G17).
- **Textbook:** double buffering.
- **Ours, under either R-A or R-B:**
  - The 3D core writes only the safe region, and the 2D engine (immune, per G20) does every move. Neither path touches the measured fault.
  - R-B beats Dell's way on 2D, which tears under Dell's single screen.
  - R-A would beat it on memory too, but only once 2D tearing is solved, and that is not measured.

**Performance:**
- R-A is the fastest on paper: no copy, +600 KiB for textures.
- R-B's cost is one rectangle copy in 3D frames that also changed 2D content: up to ~5 ms for a whole screen, much less for a status bar.
- R-C costs a whole-screen copy every 3D frame, and it fails at divide 1.

Choosing R-B over R-A is **correctness over speed**: a visible tear in 2D
frames that tear-free today. It is also the standing rule "visible UI loss:
visuals beat RAM". The copy is unmeasured at real sizes, so the cost is
stated as an upper bound only (~5 ms, whole screen).

**Correctness risk:**
- R-A: 2D tearing, which is known and visible.
- R-B: one more step in the graphics service's frame, plus the 3D area carried back to screen 1. Code that has to be right, and the device check covers it.
- R-C: a proven failure at divide 1.
- Both R-A and R-B: the loader's picture at `0x60000` lies under screen 0, so the loader's screen after a return must be looked at.

**Reversible:**
- R-B → R-A later is cheap: delete screen 1 and point 2D at screen 0.
- R-A → R-B means finding 600 KiB again after textures have taken it, which is harder once the pool is spent.
- The branch `c71-screen-place` (34b709d1) is the shared part either way. It merges with no conflicts, and is not merged.

**Recommendation: R-B.** It is the fastest option that keeps every
frame tear-free today. R-A's extra speed and memory wait on a measured
claim (2D under R20), and switching to it later is cheap.

**Would overturn it:**
- **Towards R-A:** R20 extended to 2D frames and measured tear-free on the X51v, at least 120 of 120 2D frames at both allowed clocks. Then R-A wins on memory and the copy.
- **Away from R-B:** R-B's rectangle copy measured as costing more than a frame's budget slack in `rp-today`'s typical frames.
- **R-C** returns only if amendment D ends at divide 2, which stays held.

**Device check after either ruling (the same check):**
- `rp-today` on the X51v: the shell drawn right, and the loader's screen right after it returns.
- C71's W5 partial-frame scene held to a fresh render every frame: **0 words off expected, against 1–3 today**.
- A clean result is that run's count, not proof of zero.

**Order note for ruling 3:** GC2S's divide-2 results were taken *with the
screen in the safe region*. A divide-2 ladder depends on this map change
landing first.

## Ruling 3: the gate's lift path

**In plain English:** the last 4 of 30 gate lines are all one question:
which graphics clock steps are safe. Divide 2 is drawing right at its top
steps, while divide 1 still has faults. Reid can:

- rule the ladder at divide 2 now, with divide 1 added later if the held work fixes it;
- wait for the divide-1 work;
- split the lines.

**Recommendation:** rule the ladder at divide 2, after two device proofs.
This is the fastest lift that is proven. It gives up divide 1's possible
21–29% until that work succeeds, and it is reversible.

**The four lines:**

| Line | What it covers |
|---|---|
| V2 | clocks and the memory's CL |
| V13 | the cores' divide |
| P1 | 3D at the chosen clock |
| P2 | the bus at the chosen clock |

All four are in `2700g-full-potential.md`, ADR-0035. History:
- **2026-10-22:** each was ticked on its soaks, then reopened the same day by run GC (`gpubench-0057`): divide 1 draws Gouraud wrong at every clock.
- **GC2S** (`gpubench-0082`): with the screen in the safe region, divide 2 draws all nine kinds right at 133.25 and 149.50 / 2. Divide 1 is 7 of 9 right at 74.75 / 1, and 3 of 9 above.
- **GC2CY** (2026-10-29), at 74.75 / 1: single wrong pixels in 250 renders (flat 17, layered 15, textured 0, depth 7, at 360 x 480). None at WM.

**Speed numbers that matter:**

| Comparison | Runs | Result |
|---|---|---|
| WM 99.67 / 2 against 149.50 / 2 | — | cores at 49.8 against 74.75 MHz (+50% core clock) |

## Ruling 4: the other G tests' `MBXCLK 0x6` check

**In plain English:** I flagged the other G tests' expected `0x6` as
possibly stale, like G9's was. It is not. The X51v itself reads `0x6` in
those tests, every time, because those tests switch the 3D clock on and
leave it on. G9 never switches 3D on, so it reads Windows Mobile's `0x5`.
**Recommendation: change nothing.** Optionally, add a comment to the check
saying why.

**Evidence** (device logs in `local/`, counted with grep):
- **Where 0x5 shows:** each run starts with `read back: COREPLL 0xbb1 MBXCLK 0x5` (WM's own hand-off), then `MBXCLK 0x5 -> 0x6, parameter memory ready` (`rp-glesfeat-G10.txt` lines 11–12).
- **What the controls read back:** after every control at WM's clock, `0xbb1 MBXCLK 0x6`, in every G test's device log:
  - G1: 3
  - G2: 8
  - G3: 24
  - G10: 21
  - G18: 10
  - G21: 9
  - … every log from G1 to G21 (G6's first log is empty; G6b has 12)
- G9's logs: `MBXCLK 0x5` only, since G9 never turns 3D on.
- `rp-gpubench`'s put-back reads `MBXCLK 0x6` 127 times across its device logs.
- **Bit meanings** (2700g.md): bits 1–0 enable 2D (1) or 2D + 3D (2); bits 3–2 are the divider (1 = by 2). So `0x5` is "divide 2, 2D only" and `0x6` is "divide 2, 2D + 3D".

**Rule 0:** the check's value must be the device's measured value for that
test's state. Here it already is: measured, every run, on the X51v. G9's
fix was right for G9, and copying it to the others would make their checks
**wrong on the device**.

**Performance:** none.

**Correctness:**
- Changing 0x6 to 0x5 would make the emulator check disagree with the device, which is staleness in the other direction.
- Real but separate question (not asked, and not a ruling here): should a test put back WM's 2D-only `0x5` before returning to the loader, instead of leaving the 3D clock running? That costs power, not correctness. Parked as reminder R98.

**Reversible:** trivially, either way.

**Device run needed:** no. The device proof already exists in every G test's
log. Adding the comment is docs-only.

**Recommendation: keep `0x6`.** Strike "may hide the same staleness" from the
overnight report's section 6, or let this packet correct it.

**Would overturn it:** a G test's device log reading anything but `0x6` after
its control. Then that test's check is wrong for that state and gets the
measured value.

## Ruling 5: wiring R71's pick into the per-device self-test

**In plain English:** the bus check works on Reid's X51v, and that unit
earns the faster 7/2/0 setting. Reid already ruled on 2026-10-28 (R3) that a
unit moves to 7/2/0 only through this check, and that failures stay at
7/3/1. So the policy is decided; this ruling is about wiring it in now.

**Recommendation:** wire it in, after one more device run: the check run at
a setting *known to fail* on this unit, to prove it actually catches a bad
bus on real hardware. A second unit isn't needed for wiring, because every
unit has to pass its own check first.

**Evidence:**
- **Self-test run** (`local/rp-cs3bus-selftest.txt`):
  - MSC1 as WM's (`0x24842481`).
  - 7/3/1: 0 misses in 1,572,864 transfers.
  - 7/2/0 cold: 0 misses.
  - 300 s of traffic at 7/2/0 (1,674 rounds of a 1.2 MB flush and a 2D fill): 0 misses.
  - 7/2/0 warm: 0 misses.
  - Pick: 7/2/0. MSC1 put back.
- **Host tests:**
  - a fault of 1 in 1,000 transfers is caught;
  - a check under 100,000 transfers never passes;
  - 7/2/0 is chosen only when default, cold and warm are all clean.
- **Run 2's grid** (`rp-cs3bus-run2.txt`, memory-timing.md):
  - every point with RDF 4 or 3 **reads wrong, every word**, with no hang reported;
  - every control at WM's timing after a failing point was clean ("a failing point leaves nothing behind").
- **The speed:** a 1.2 MB flush takes:

  | Setting | Flush time |
  |---|---|
  | WM's 8/4/2 | 35.5 ms |
  | 7/3/1, the default | 31.9 ms |
  | 7/2/0 | 28.8 ms |

  7/2/0 against the default is **3.1 ms, 9.7% less**. Against WM it is 19% less. (The brief's "about 10% faster than WM" is the default's gain over WM. 7/2/0's own gain over the default is the 9.7%.) The gain is in uploads and flushes, not 3D render time.

**Rule 0:**
- **Original way:** WM uses one timing, 8/4/2, for every unit.
- **Textbook:** the datasheet's minimum plus a guard band.
- **Ours:** each unit measures its own bus and earns the faster timing only on proof.
- **Why it wins:** 9.7% on uploads where proven, and no unit is ever run at an unproven timing.
- **The gap:** this check has never failed on real hardware. Its host tests prove the logic. Nothing yet proves its patterns detect a real bad bus on the device. A check that has never failed on silicon could be passing everything silently.

**Performance:** 3.1 ms a full flush (9.7%) on every unit that passes.

**Correctness risk:**
- A unit marginal at 7/2/0 that passes at docking and fails later, hot, corrupts uploads silently.
- That is why the warm phase exists. Five minutes doesn't cover the hottest day.
- RDN and RRR at 7/2/0 sit at the PXA's minimum code. Their margin is the clamp, not a measured margin (memory-timing.md).

**What the self-test must do on failure:**
- stay at 7/3/1 for that unit;
- log which phase (default, cold or warm), which pattern, the first failing address, expected against read, and the miss count;
- keep the result with the unit's self-test record, so it is visible and not re-tried silently every boot;
- re-run only when the self-test reruns (first docking, OS update, or a manual request);
- never fall back below 7/3/1 on its own. A miss **at 7/3/1** is a device fault to report, not a timing to tune.

**Reversible:** yes. MSC1 is set at boot, so un-wiring returns every unit to
7/3/1 on the next boot. Nothing is written to hardware permanently.

**Negative control done, 2026-10-29:** at 4/2/0 the check reported
786,431 of 786,432 reads wrong and kept 7/3/1. One thing for the wiring: the
warm phase still ran after the cold check failed, and the 2D fill's
time-out was logged as "4294967295 misses". The wired check must skip warm
after a cold failure, and must name a 2D time-out as a time-out, not as a
count.

**Recommendation:** **wire it in, after a negative control.** One device run
of the self-test mode at RDF 4 (for example 4/2/0, which run 2 showed reads
wrong every word, with no hang and clean controls after). Expected result:
misses reported, pick 7/3/1, MSC1 put back. A second unit (the X50v, or
another X51v) would show how common 7/2/0 is, but it isn't needed for
wiring.

**Would overturn it:**
- The negative control **passing** (no misses at RDF 4). Then the check is blind, and nothing gets wired until it's fixed.
- Any unit that passed showing a CS3 miss later (for example in a runtime upload hash). Then the warm phase gets longer or hotter, or 7/2/0 goes back to off.

## Ruling 6: the ratchet's floors (R97)

**In plain English:** three numbers came in barely over their floors, and
two memory numbers got much faster for no known reason. All five are memory
paths, so one shared cause is likely. Approving slower floors without a
reason, or banking faster ones without a reason, would both write a guess
into the ratchet.

**Recommendation:** hold all five and settle R97 first, with one decisive
device run.

**Evidence** (`local/perf-2026-10-29.txt` against `docs/perf-floors.md`; lower
is better):

| Number | Floor | 2026-10-29 | Change | File's tolerance | Note |
|---|---|---|---|---|---|
| `probe.frames_fill_drain_1024` | 417,291 | 420,553 | +0.78% | 0.143% | 5.5x its tolerance |
| `probe.memcpy_sdram_to_sram_64k` | 396,722 | 398,537 | +0.46% | 0.154% | 3x |
| `probe.gfx_flush_vga` | 17,794,051 | 17,795,589 | +0.009% | 0.0035% | **already approved slower once** (2026-10-22, option A) |
| `probe.chase_sdram_256k` | 2,013,192 | 1,284,038 | −36.2% | 0.0306% | **also approved slower once** (2026-10-22) |
| `probe.chase_sram_256k` | 454,306 | 345,884 | −23.9% | 0.1355% | |

**Rule 0 / correctness:**
- A floor is a measurement of a known set-up.
- A 24–36% jump in a memory chase with no code reason is much more likely a *set-up* change than a speed-up. Candidates:
  - mapping or TLB (the C4 lock-down `32c7adfc` and V7's mappings `84b2ed89` landed in the probe since the floors);
  - clocks or memory registers as the loader leaves them after other runs;
  - the probe's working set.
- If it is a set-up change, the floors measured a different thing, and both "faster" and "slower" are artefacts.
- Approving `gfx_flush_vga` slower a second time would also make a small creep look normal.

**Performance:** none directly. The risk is a ratchet that stops catching
real regressions, or a fake gain banked.

**The investigation that settles R97** (one device run, Reid's go):
1. On the X51v, in one session, run the probe at the floors' commit (`370f6c87`) and at today's (`64063274`), back to back, cold.
2. Have both dump the state they ran under: CCCR / CLKCFG, MDCNFG, MDREFR, MSC0–2, CP15 control and the TLB lock-down state.
3. **If the old binary still gives the old numbers:** it's a code change. Bisect the probe and runtime commits since 2026-10-22.
4. **If the old binary gives the new numbers too:** it's device or loader state. Diff the dumped registers against the floors' run.

**What happens in each case:**
- **A set-up change that is intended** (for example the TLB lock-down is the shipped design): re-floor all five from fresh noise runs (`perf noise 5`), with Reid's approval, noted as "set-up changed: `<commit>`", not as gains or losses.
- **A set-up change that is unintended** (a register left behind by a test): fix it, rerun, and the old floors should hold.
- **The faster numbers are real and explained:** bank them with `--update`, with the reason written.

**Settled on the device 2026-10-29** (see "Device runs since"). It is the
"set-up change that is intended" case:

- **Both chases:** commit `0b2e1be2` changed the benchmark itself. **Recommendation:** re-floor both, noted "benchmark changed: `0b2e1be2`, one word load a hop", not as a gain.
- **The three slower ones:** none is a device regression; the old probe shows the same picture. **Recommendation:** no approval of slower floors. Instead re-measure noise and floors from the current build (`cargo xtask perf noise 5`, about 25 minutes on the X51v), so the tolerances reflect the real spread across runs. Floors written only on Reid's yes.

What follows was written before the device run:

**Recommendation, per number:**
- **All three slower ones: hold.** Do not approve them now.
  - `frames_fill_drain` (5.5x its tolerance) is the one most likely to be a real change.
  - `gfx_flush_vga`'s slip is 1,538 on 17.8 million (0.009%). If R97 finds nothing, the right fix is re-measuring its noise, not a second approval.
- **Both faster ones: hold.** Do not bank them.

**Would overturn it:** the back-to-back run showing the old binary
reproducing its old numbers *and* the new code having no mapping or clock
difference. Then the three slower numbers are plain noise against tight
tolerances, and approving them (or re-measuring noise) is fine.
