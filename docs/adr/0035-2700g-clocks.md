# ADR-0035: The 2700G's clocks: past Dell's, through a self-test on every device

- **Status:** **Accepted (owner, 2026-10-22: "I accept what you think is
  best")**, the self-test's four questions voted the same day (1A, 2A, 3A,
  4A: [docs/design/clock-selftest.md](../design/clock-selftest.md)).
  Closes the gate's lines P1, P2, V2, V12, V13 and V14 (phase 5).
- **Date:** 2026-10-22

## In plain words

Windows Mobile runs the 2700G's system clock at 99.67 MHz and its 2D and
3D cores at half that. On the owner's X51v we measured the chip running
right, for 20 minutes under full stress, warm and cold, with the cores at
the full system clock and with the system clock at 133.25 MHz: the 3D
core then draws about twice as fast (35.6 ms a frame becomes 17.9). One
device isn't every device, so RetroPane doesn't ship a faster clock as a
constant: each device tests itself once, on its first docked night, and
runs one step below the fastest setting it passed. Any later sign of
trouble drops it back to Windows Mobile's setting, which every X51v has
run for years.

## Context: what we measured (one X51v, the owner's)

| Run | What it showed |
|---|---|
| G3, G4 (2026-10-20) | The cores at divide 1 (Dell's driver caps them at 75 MHz) run right at 99.67 MHz: 2D 1.89x, 3D 1.81x faster. Dell's CL3 rule above 100 MHz breaks the 3D core every time; CL2 runs right to 133.25 MHz (short checks). Writes to `LMTYPE`/`LMREFRESH` can be lost (V12). |
| G5 (2026-10-20) | Every step from 49.83 to 133.25 MHz right with the cores at divide 1, both passes; a 60 s soak at 99.67 / 1. |
| GS warm (2026-10-22, `gpubench-0052`) | 20 minutes each at 99.67 / 1 and 133.25 CL2 / 1, every round stressed (bus, memory patterns, 2D fill and copy, 3D pixel-exact, the CPU streaming SDRAM, a 16-bit screen scanning out): 1,320 rounds, 0 BAD, no drift, the registers held, no underrun. |
| GS cold (2026-10-22, `gpubench-0053`) | The same after an hour asleep: 0 BAD, the same times. |
| GV (2026-10-22, `gpubench-0054`) | The local memory runs on the system clock (V1): memory speed is the system clock, compute speed the cores. |

With the shell's 16-bit screen on (GS): 3D 35.58 ms at Windows Mobile's
setting, 22.85 at 99.67 / 1, 17.95 at 133.25 / 1; a full-screen 2D fill
6.35, 4.23, 3.09 ms.

Every number above is ours, measured on the X51v. Dell's settings (the 75
MHz cap, CL3 above 100 MHz, 99.67 MHz as the ceiling) were leads; the
measurements overturned the first two.

## Measured since (2026-10-22, run FT2 at 133.25 / 1, `gpubench-0056`)

**A finding against this ADR's evidence:** at 133.25 MHz CL2 with the
cores at divide 1, an RGB565 render with a full-screen Gouraud background
and a textured quad wasn't repeatable even alone (104-365 words of 153,600
differ between two renders; exact at Windows Mobile's clock). Run GS's
scene (32-bit, textured, translucent, flat; no Gouraud) was exact at the
same setting for 40 minutes. So the self-test's round must cover every
kind of drawing the OS does (target formats, Gouraud, every texture
format, blending), not GS's one scene, and on the owner's unit 133.25 / 1
fails such a round: its ladder result changes. The decision's structure
(a per-device test, a margin step, the fallback, the guard) is unchanged;
the evidence for the faster settings is reopened until a run maps which
steps draw every content right (2700g.md, "2D and 3D at once"). For the
owner: results, not a decision.

**Run GC, the content map (2026-10-22, `gpubench-0057`): the cores at
divide 1 draw Gouraud shading wrong at every system clock, 99.67 MHz
included; textures, blending and flat fills are right at every setting;
the cores at divide 2 under a 133.25 MHz system clock are right but one
word in two of three ARGB8888 Gouraud renders.** So every step of this
ADR's ladder (all at divide 1) fails on the owner's unit, and the
ladder as decided would always fall back to Windows Mobile's setting.
The structure stands (a per-device test of every kind of drawing, a
margin step, the fallback, the guard); **the ladder itself is reopened
for the owner**: two dimensions (the system clock, which is the
memory's, and the cores' divider), mapped next (the cores at divide 2
under every system clock, and the cores at divide 1 at or below 75 MHz).
Gate lines P1, P2, V2 and V13 are reopened (partial) until then.

## Decision

1. **The self-test sets the clock** on each device
   ([docs/design/clock-selftest.md](../design/clock-selftest.md), as
   voted): a ladder of five settings (Windows Mobile's 99.67 / 2; then
   99.67, 108.33, 117.00 and 133.25 MHz with the cores at divide 1), run
   GS's round for **5 minutes a step** after a two-minute warm-up, the
   first failure ending the ladder; **one step below the fastest that
   passed** is used (on the owner's unit, if 133.25 passes again: 117.00
   / 1). It runs **in the background the first time the device sits
   docked with the screen off**; until then, Windows Mobile's setting.
2. **Windows Mobile's setting is the fallback**: 99.67 MHz, the cores at
   divide 2, CL2, Windows Mobile's memory timing. Used before the test,
   after any failure, on a device-fingerprint mismatch, and when the user
   turns the automatic setting off.
3. **CL2 always.** Dell's CL3 rule above 100 MHz isn't used (V14: it
   breaks the 3D core).
4. **Every memory-controller write is read back and rewritten, up to
   three tries; a write that never holds fails the step** (V12;
   `clock::set_speed`'s `WRITE_TRIES = 3`, the PLL's lock waited for at
   most 50 ms; GS: once held, they stayed for 40 minutes). A bus that
   freezes outright (a read that never returns) is the watchdog's: the
   marker (point 5) records that step failed.
5. **A hang counts as a failure**, recorded by a marker written before
   each step, so a step that froze the device is never run again
   unattended.
6. **The guard while running:** while the GPU is idle, **one small check
   a second at most** (a 64 x 64 render against its picture, or a 4 KiB
   memory pattern, ~1 ms each: 0.1% of the GPU's time), rotating through
   every kind of drawing so all are covered **every ~10 s**; when the GPU
   is never idle (a game), **one check every 10 s** between frames. So a
   chip that starts to fail is caught within ~1 s idle, ~10 s in a game,
   a glitched frame or two at worst. Any error, a recovered GPU
   hang, the underrun flag outside a clock change, or an unexplained reset
   drops the clock to Windows Mobile's at once, logs it, schedules a
   re-test and says so quietly in Settings.
7. **Re-tests:** after an update to the GPU driver or the clock code,
   after the guard trips, on a device-fingerprint mismatch (the card moved
   to another X51v, or the X50v), and on request in Settings.
8. **The clock changes only where the display can take it:** at start-up
   before the shell shows, during the test (its own screen checks), and
   on the guard's drop. A change parks the system clock on the 13 MHz
   reference for a moment, which G4 found can stop scan-out (`DINTRS` bit
   4); every change is followed by the underrun flag's check and Dell's
   clear (run U), and the guard's drop path is tested for it before it
   ships.

**Added by ADR-0034 amendment P (owner, 2026-10-24, P3):** the self-test
also measures **the safe region**: how far into local memory the display
may read while the 3D core renders without corrupting it (`rp-glesfeat`
G18/G19's ladder on this device; ~`0xAE000` on the owner's X51v, a
hypothesis that it is the on-die frame buffer to settle), stored with the
device fingerprint; until measured, the smallest proven layout (the screen
alone at `0x0`).

## The red-team review (2026-10-22)

The owner's second reviewer read this ADR; its three points and the
owner's votes (the same day: "Yes to all three going into the ADR and
design doc"):

1. **Bound the rewrite loop:** already bounded in code (three tries, the
   step fails); the wording of point 4 fixed. Accepted.
2. **Justify 5 minutes a step:** every failure seen so far was immediate:
   CL3 broke 3D on every check, G2's 108 MHz CL3 hung at once, G4's
   display went dark at the clock change, and FT2's Gouraud scene failed
   on its first render at 133.25 / 1, a setting GS's scene passed for 40
   minutes. No drift was seen (GS's minutes within 12 us over 20 minutes;
   cold equal to warm). The gap was content, not length, and the round
   now covers every kind of drawing. **Option A kept (5 minutes), voted
   by the owner:** "B and C buy margin against a failure mode with zero
   observed evidence." The honest limit stays written: one unit, room
   temperature, never a hot day; the guard covers drift later.
   Alternatives: B, 20 minutes on the top two steps (+30 minutes); C, 20
   minutes on every step (~1.5 hours).
3. **The guard's interval as a number:** point 6 now says it (one check
   a second idle, every kind covered in ~10 s, one every 10 s in a game).
   Accepted.

## Security

The self-test's result is stored on the device and read at every start:
it is **input**, not trusted. It is checked (its format, a checksum, the
device fingerprint, a step number in range); anything wrong means Windows
Mobile's setting and a re-test, never a guess. A forged or corrupted
result can at worst select a clock the chip can't run, which the guard
catches as errors (the 2700G's memory holds pictures and commands, not
the user's files). Nothing here is reachable from the network. The
self-test's markers and results stay in the OS's own storage, never in a
shared folder of the card (the card is shared: shared-card rule).

## Open before it ships to anyone

- **A freeze mid-test on today's SD-card stage ends in Dell's
  restore-factory-settings prompt** after the watchdog reset, which a
  user must never be asked to answer. Before the self-test reaches anyone
  but the owner, the reset path needs its own answer (in the flash-install
  work or the loader). Until then it runs only on the owner's devices.
- **The device fingerprint:** which hardware identity (the Wi-Fi chip's
  MAC address is a candidate), verified on the X51v and the X50v.
- **Other units:** the design exists because one unit isn't the
  population; the X50v, once it runs RetroPane, is the second test.

## What it doesn't decide

- **Battery** (phase 9): a faster clock costs power while the GPU works;
  the power lines decide when to run slower on battery. The self-test only
  finds each device's safe ceiling.
- **The CPU's own clock** (CPU gate line C2) is separate; the same design
  would carry it as its own ladder.

## The four lenses

| Lens | Effect |
|---|---|
| 🔁 Iterate | Each rule is a measured run (G3-G5, GS, GV); the self-test reuses run GS's checks; the ratchet records the speed |
| ✨ Modernize | Per-device calibration with a guard and fallback, as modern GPUs and phones boost within tested limits |
| 🗄️ Legacy support | Invisible to Windows Mobile programs: they get the same 2700G, faster; the fallback is Windows Mobile's own setting |
| ⚡ Better / faster | About twice the 3D speed and 1.5-2x the 2D on a chip that passes, measured, on hardware Dell capped |

## Alternatives considered

- **Ship 133.25 / 1 as a constant:** the fastest, proven on one unit;
  rejected by the any-Axim rule.
- **Ship Windows Mobile's setting:** safe and half the speed; rejected:
  the measurements show the margin on this chip, and the self-test makes
  using it safe per device.
- **Use the fastest step that passed (no margin step):** the owner chose
  the margin (vote 1A).

## Consequences

- The self-test and the guard are built in phase 5 with the GPU driver;
  their checks (the emulator with a forced failure and a reset mid-step,
  a mutant per rule, then the whole ladder on the X51v) are in
  [docs/design/clock-selftest.md](../design/clock-selftest.md).
- The performance ratchet measures at the self-test's chosen setting on
  the owner's unit, and records which setting that was.
- `rp-gpubench`'s run GS becomes the self-test's round: one set of checks,
  not two.
