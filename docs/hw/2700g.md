# Intel 2700G ("Marathon") on the Dell Axim X51v

> Spec v0.2, 2026-10-10. Facts only, per [`../CLEANROOM.md`](../CLEANROOM.md).
> **Sources:** (A) static analysis of Dell's `ddi_2700g.dll` from the user's
> own ROM (WM6.1 A08; identical code in L11 and WM6.5.5 L16), (B) the old Linux
> `mbxfb` register header (register names), (C) AxDroid board code.
> Spec and analysis were done by the same AI session, so this spec should be
> reviewed on its own before drivers rely on it.

## Rule: the framebuffer is write-only

Measured on the owner's X51v (docs/perf.md, 2026-10-11): a pattern fill
that read the framebuffer took 61 ms; building rows in RAM and only
writing took 14.5 ms, the same as a solid fill. Reading 2700G memory is the
slow part. So: compose in SDRAM, write only changed (dirty) rectangles to
the 2700G, never read it back. Every display path follows this
(docs/design-brief.md).

## LCD panel timing (3.7" VGA, 480 × 640)

The driver carries a 32-entry panel table (80-byte records: resolution, refresh,
pixel clock, line rate, horizontal/vertical front porch, sync, back porch,
borders, panel size). Decoding was checked against entry 5, which is standard
VESA 640 × 480 @ 60 exactly (16/96/48, 10/2/33, 25.175 MHz).

The X51v panel's working timings, consistent between Dell's table (entry 3) and
AxDroid's independently tested values to within 1 pixel:

| Parameter | Dell entry 3 | AxDroid |
|---|---|---|
| Active | 480 × 640 | 480 × 640 |
| Horizontal front porch / sync / back porch | 88 / 64 / 16 | 87 / 64 / 17 |
| Vertical front porch / sync / back porch | 1 / 2 / 1 | 4 / 2 / 1 |
| Total | 648 × 644 | 648 × 647 |
| Pixel clock | 23.5625 MHz | (PXA divider value) |
| Refresh | 55 Hz (line rate 35.648 kHz) | — |

Confidence: **likely**. The mapping from `Panel = 10` to table entry 3 hasn't
been traced in code yet. The CPLD reports the panel maker in register `0x1E`
(Sharp or Samsung, per AxDroid).

## Display programming model

Field layouts from the public Linux `mbxfb` definitions (B), the encoding as
used by that driver. All timing fields are 12 bits wide, at `[27:16]` and `[11:0]`.

| Register | Offset | Fields |
|---|---|---|
| `GSCTRL` | 0x2000 | `[30:27]` pixel format (0 indexed, 4 ARGB4444, 5 ARGB1555, 6 RGB888, **7 RGB565**, 8 ARGB8888), `[26]` gamma enable, `[21:11]` width − 1, `[10:0]` height − 1 |
| `GBBASE` | 0x2020 | graphics base (0 in mbxfb) |
| `GDRCTRL` | 0x2040 | `0x00FFFFFF` in mbxfb |
| `GSCADR` | 0x2060 | `[31]` stream enable, `[22:0]` plane start address in local memory **/ 16** |
| `GSADR` | 0x20C0 | `[31:22]` stride: bytes per line / 16 − 1; `[21:11]` X start; `[10:0]` Y start |
| `DSCTRL` | 0x2154 | `[31]` sync generator enable, `[5]` blank polarity, `[3]` VS polarity, `[1]` HS polarity |
| `DHT01` | 0x2158 | `HBPS` = hsync; `HT` = total |
| `DHT02` | 0x215C | `HAS` = hsync + back porch; `HLBS` = same |
| `DHT03` | 0x2160 | `HFPS` = HAS + active; `HRBS` = same |
| `DVT01..03` | 0x2164–0x216C | same scheme vertically (`VBPS`/`VT`, `VAS`/`VTBS`, `VFPS`/`VBBS`) |
| `DHDET` / `DVDET` | 0x2314 / 0x2318 | display enable start/end: `HAS`/`HFPS`, `VAS`/`VFPS` |
| `DVECTRL` | 0x2310 | `VEVENT` = VFPS, `VFETCH` = VBPS |

The conventional framebuffer location is local-memory offset `0x60000`.

**X51v panel encoded:** `HBPS` 64, `HAS` 80, `HFPS` 560, `HT` 648; `VBPS` 2, `VAS` 3,
`VFPS` 643, `VT` 644. A 480 × 640 RGB565 plane has stride field 59 (960 bytes / 16 − 1).

Not yet specified: PLL/pixel-clock programming (`DISPPLL`, `PIXCLK*`), local
memory power-up (`LMPWR`) and `SYSCFG`. Under Windows Mobile these are already
configured when RetroPane is launched from SD.

## Physical mappings made by the WM driver

The driver maps hardware through a helper that calls `VirtualAlloc` +
`VirtualCopy` with `PAGE_PHYSICAL` (address >> 8), optionally `PAGE_NOCACHE`:

| Physical | Size | What |
|---|---|---|
| `0x48000000` | 4 KB | PXA27x memory controller (static memory timing for the 2700G's chip select) |
| `0x41300000` | 4 KB | PXA27x clock manager |
| 2700G windows | computed | from a config structure built from `VLIOChipSelect`/`SRAMChipSelect`; five mappings (to be traced) |

It also uses `InterruptInitialize`/`InterruptDone` (the "MarathonISR" interrupt
thread), `KernelIoControl` (OAL queries), `SetKMode`, `VirtualSetAttributes` and
`CacheRangeFlush`.

## After the hand-off: no settle time (item 72, 2026-10-15)

What a program must wait for before its first 2700G register read, after
HaRET's hand-off from Windows Mobile or the loader's from an image.

| Fact | Confidence | Evidence |
|---|---|---|
| Images that read the 2700G's registers at once after HaRET's hand-off hung in some runs (`rp-probe` once, `rp-usb` twice in a row, docked); images that first spent ~1 s writing its memory never did | confirmed (as observed) | P, 2026-10-11 (commit `0f2d0da`) |
| The hangs were not the 2700G's: 21 minutes later images were found hanging at random early points (before the MMU was on, at the 2700G, before drawing) and only while docked with USB active: Windows Mobile's USB DMA still writing RAM after the hand-off. `_start` has stopped all 32 DMA channels and the UDC as its first act since | likely | P, 2026-10-11 (commit `87d8d5b`); no hang at the 2700G reported since, but the 500 ms wait stayed and masked any |
| Writing 2700G memory right after the hand-off never hung (the start-up colour beacons of `rp-light`, `rp-usb` and the loader run before any register read) | confirmed | P, since 2026-10-11 |
| A DMA channel stops once the transfer in flight is done after `RUN` is cleared; `DCSR.STOPINTR` (bit 3) says it has stopped | likely | PXA27x Developer's Manual, DMA chapter (the emulator models `STOPINTR` the same way) |

**RetroPane (2026-10-15):** the fixed 500 ms wait (`SETTLE_US`, paid by the
loader and by every image it starts) is gone. `_start` records which DMA
channels were running (`rt::handoff`, read only with the DMA clock on; the
UDC is stopped but not read: a read of an absent block faults before any
handler exists); `devices::take_mbx` waits until those
channels report stopped (`rt::wait_handoff_dma`, at most 10 ms, normally
microseconds) and records what it found and when (`devices::mbx_handoff`;
the loader's `handoff` command, `rp-handover`, `rp-light`). Not suspected
and not waited for: the 2700G's PLL or local memory powering up (Windows
Mobile's screen is being scanned out from that memory when HaRET runs) and
its driver being busy (Windows Mobile is stopped, interrupts masked, before
HaRET jumps).

**Device (P, 2026-10-16, `rp-handover` runs 1-2):** the loader-to-image
hand-off without the wait: no DMA left running, the 2700G handed out 370 us
after the image's start (was at least 500 ms), the run clean.

**Device (P, 2026-10-16, the loader installed from main 98ae4fa, three
soft resets docked):** HaRET's hand-offs without the wait: every time no DMA
channel was running (Windows Mobile's or HaRET's stop leaves none), no hang,
the 2700G taken at 585-588 ms and the loader ready at 623-627 ms; Windows
Mobile's CPLD table adopted each time with the same values (cpld.md). The
2700G comes that late because of what the loader does before it (card
set-up, the SD DMA self-test, the USB detach), which took ~585 ms on the
device against ~200 ms in the emulator; the old 500 ms wait hid inside it,
so the loader's own boot didn't get faster here, while every image it
starts did (`rp-handover`: 370 us instead of 500 ms). **Settled 2026-10-17 (device, `handoff`'s stage times):** the loader's ~585 ms
before the display were 103 ms of SD card, 24 ms of DMA self-test and file
system, and **457 ms of CF attach** (a 308 ms power-off and a 110 ms power-up
of a slot Windows Mobile had left powered). With the warm attach (cf.md) the
CF stage is 25 ms: the 2700G is taken at 152 ms and the loader is ready at
347 ms, from 583 ms and 629 ms.

## Who draws Windows Mobile's fills (measured, 2026-10-13)

Measured on the owner's X51v under stock WM 6.1 by `tools/wmbench`
(`rp-wmbench` v3, `rp-wmgpu`; observation only, read-only mappings):

| Finding | Confidence | Evidence |
|---|---|---|
| WM's full-screen `PatBlt` fills are queued: 20 return in ~2 ms and finish later | confirmed | (P) 20 fills timed 0.1 ms each; a pixel read after them waits ~62 ms; with the read, 3.2 ms per fill |
| Something other than the CPU does the filling, at ~190 MB/s | confirmed | (P) a lowest-priority counting thread kept 100-110% of its idle rate while 20 fills drained (3 rounds), and the queue was empty after 100 ms; the CPU's own writes to this memory reach ~32-41 MB/s even write-combined (docs/perf.md) |
| Not the PXA270's DMA controller | likely | (P) no channel's `DCSR` showed RUN without STOPSTATE in ~20,000 samples while fills drained (nor idle); the probe didn't log raw values to prove the mapping live (next probe does) |
| So: the 2700G itself fills (a 2D engine, or the MBX core drawing a quad or clearing) | likely | the two above; the driver's run-time-generated "bytecode" (above) may be command streams for it rather than CPU code |
| Reading the whole 128 KB register block (`0x0FFE0000`) word by word freezes WM | confirmed | (P) the probe's third phase hung the device (soft reset recovered it); some offset there has read side effects or is a bus hole. Read only known registers |
| Full-screen `BitBlt` from an off-screen bitmap: 5.1 ms; text: 2.5 ms per 54-character line | confirmed | (P) rp-wmbench v3 |

Consequence for RetroPane: the CPU fill (14.5 ms full screen) is ~4.5x
slower than what the chip already does for WM, with the CPU busy
throughout. Item 69's next step is to find which unit draws (2D engine or
MBX) and its command path, reading only registers the driver itself
touches.

### The drawing path in Dell's driver (static analysis, 2026-10-13)

From (A) `ddi_2700g.dll`, following the 2D work rather than the CPU blit
code. Facts as found; no code from the driver.

| Finding | Confidence | Evidence |
|---|---|---|
| The driver contains a PowerVR-style services layer: one initialisation routine (`0x0211be7c`) maps five regions and keeps their addresses in a 0x180-byte structure (fields `+0x2c`, `+0x44`, `+0x48`, `+0x58`, `+0x68`), with mapping flags 9 for some and 12 for others (registers versus memory windows: to confirm); a pointer at the first region + `0x12c` is kept separately | likely | (A) |
| WM's fills are drawn by the **MBX 3D core**, not a separate 2D engine: the functions that stream the most data (`0x0211a670`, `0x02117d9c`) set up a render target per surface (width and height chosen by screen rotation 0/90/180/270), size a tile grid, and fill region arrays with tile coordinates (x and y in 7 bits each, `x \| y << 8`) and 2400-byte region buffers, the shape of a tile-based renderer's region headers; one refers to the fixed system-RAM address `0xA8800000` | likely | (A); fits the measurement above (the CPU free, no DMA, ~190 MB/s) |
| Consequence for RetroPane: there is probably no shortcut "2D fill" to reuse: GPU drawing (item 69 step 4 on) is the MBX bring-up itself: register base, the render-start register, the region and parameter buffers, a rectangle drawn as geometry | likely | the two findings above |

**Registers (A and P, 2026-10-13, corrected the same night).** The
driver's register helpers (read `0x0211ed74`, write `0x0211ed7c`, a table
of offset/value pairs `0x0211ed8c`) take a base pointer, and are used on
**two different register blocks**:

- the 2700G **system block at `0x0FFE0000`** (the one RetroPane already
  drives): offsets with a Linux (B) name, among them `SYSCFG 0x000`,
  `SYSCLKSRC 0x02c`, `PLLSTAT 0x040`, `VOVRCLK 0x044`, `PIXCLK 0x048`,
  `M24CLK 0x050`, **`MBXCLK 0x054`** (the driver writes 0, then
  `((divider - 1) << 2) | enable`; **corrected 2026-10-14**: bits 1-0 are
  an enable, not a clock source: 0 none, 1 2D only, 2 2D and 3D, Linux
  mbxfb's `MBXCLK_EN`; Windows Mobile idles at `0x5`, 2D only), `LCD_CONFIG 0x060`,
  `ODFBPWR 0x064`, the PWMs `0x204`-`0x228`, **`ID 0xff0`**, the local-memory
  controller `0x1004`-`0x101c`, display registers `0x2060`-`0x2154`, and
  **`DVLNUM 0x2308`** (the scan line, polled: the vsync wait);
- the **MBX core's own block**, the first region the services layer maps
  (its structure's `+0x2c`), at a physical address not yet found. It
  identifies itself the ARM PrimeCell way: the bytes at `0xff0`-`0xffc`
  must assemble to `0xB105F00D`; then the part number from `0xfe0`/`0xfe4`
  (`0x910` or `0x930` accepted), else a core ID at `0xf00` (top byte 1,
  next byte 1 or 2) and `0xf10`. Offsets `0x080`, `0x0c0`-`0x0c8`, `0x12c`,
  `0x134`, `0x300`-`0x30c`, `0x6ec`, `0x804`-`0x85c`, `0xf00`, `0xf10`,
  `0xfe0`-`0xffc` are most likely this block's.

**Measured under WM (P, `rp-wmgpu` v3-v6):** read one at a time, the
system block's named registers read fine: `SYSCFG 0x0`, `SYSCLKSRC 0x2`,
`PLLSTAT 0x7`, `VOVRCLK 0x0`, `PIXCLK 0x1`, `M24CLK 0x2`, **`MBXCLK 0x5`**
(source 1, divider 2: the core's clock runs while WM idles), `LCD_CONFIG
0x2efa0000`, `PWMCFG 0x3`, PWM0/1 `DIV 0 DUTY 0 PER 4`, **`ID
0x01727189`**, `LMPWRSTAT 0x0`, `DSCTRL 0x8000002a`, `DVT03 0x02830283`,
`0x2060 0x80000000`, `0x2064 0x01000000`, `0x2100 0x0`, `0x300 0x3`, `0x304
0x3`. **Reading `0x0FFE0000 +` `0x12c`, `0x30c`, `0x85c` or `0xf00` froze WM**
each time: offsets of the MBX block, read on the system block, where they
are most likely unimplemented. **Rule: reading an unimplemented address in
the 2700G's register block hangs the bus** (under Windows Mobile; under
RetroPane's loader, `rp-gpubench` run H1 and H2, 2026-10-20, a read of the
system block's `0x12C` returned 0 and didn't freeze, twice: why it differs
is open, so the rule stands: read only registers known to exist) (as v1's blind scan of all 128
KB did). Read only registers known to exist. (Explanations written earlier
that night, an interrupt status cleared by reading, then a clock-gated
core, were wrong: the driver's own code showed the two bases.) DMA idle
while WM fills (raw `DCSR` 0x8: the mapping was live).

**The MBX block's address (A, then P).** The services layer computes each
core's registers from the 2700G's base (`0x0C000000`): type 0, the MBX, at
base + `0x3FE4000` = **`0x0FFE4000`** (4 KiB); type 1 at `0x0FFE2000` (the
display registers, where Linux has them: the cross-check), type 2 at
`0x0FFE3000` (the video decoder: confirmed 2026-10-14, "The MVED1 video
decoder"). The MBX gets three more 4 KiB
windows from a second base (`+0x4000`, `+0x5000`, `+0x6000`; most likely its
command ports), not yet placed.

**Measured under the loader (P, `rp-mbx`, 2026-10-13): first contact.**
With the clock as WM left it (`MBXCLK 0x5`), reading the MBX block works:
`0xff0`-`0xffc` read 0 (not a PrimeCell), so the driver's other branch
applies: **`0xf00` = `0x01020000`** (top byte 1, then 2: the driver accepts
1 or 2 there; most likely the core variant) and **`0xf10` = `0x00010000`**
(most likely the revision). The core is at `0x0FFE4000`.

**Confirmed under WM (P, `rp-wmgpu` v7):** at the right base nothing
freezes: `0xf00 0x01020000`, `0xf10 0x00010000`, `0x12c 0x0`, `0x30c 0x0`,
`0x85c 0x00008000`, all read while WM runs. While WM drew 20 full-screen
fills, **MBX `0x12c` changed 22 times** (first to `0x00950000`, back to 0 at
the end) and never while nothing was drawn: the core's activity or status
register, set while it renders. The other MBX registers held still.

**Correction (A, 2026-10-13, later):** the 15-pair table above belongs to a
second render context (stored at the driver's device `+0x160`), built for a
planar-YUV conversion or rotation job (surface height 1.5 × h, three planes,
rotation codes), not for WM's fills. Its values: `0x608` region array,
`0x60c` object buffer, `0x654`/`0x658` tile counts, `0x660` stride / 4,
`0x650` 6 (most likely 32 bpp). The 3D context that does draw rectangles
(device `+0x15c`, built at `0x02117d9c`) is kicked with a register table the
*client* builds, outside this DLL, so its target registers stay unknown.
Its formats, as found: region entries are two words (`x | y << 8`, bit 31 =
last; the address of one control stream shared by every tile); control
words `0x6xxxxxxx` point at objects (offset in words in bits 20-0), `0xF0000000`
ends the list; objects store four vertices as all x/y pairs, then four Z,
four 1.0, four colours. The family resemblance to the Dreamcast's PowerVR2
(link and end words, last-region bit, ISP/TSP-style state words, texture
sizes as log2 − 3) is strong. Kept for later (textured drawing); the 2D
engine below is the simpler way to fill and copy.

### The MBX 2D engine (static analysis, 2026-10-13)

WM's `PatBlt`/`BitBlt` go to a **2D engine** fed through a command window,
not to the 3D core. Facts from (A); no code copied.

**Dell's interrupt handling (A, bounded look, 2026-10-14).** No 2D
completion interrupt is used anywhere: fences are polled in every path.
The interrupt thread (`0x0211d440`) waits on SYSINTR **27** (hard-coded;
its GPIO is in the OAL, not extracted), writes `MINTENABLE` (system
`+0x18`, never read) `0x000F` around the handlers and `0x800F` after (bit
15 likely the master enable). The MBX ISR (`0x021192b4`) acts on `0x12c`
bits 0, 2, 4-10; bit 10 drops a clock vote (it can stop `MBXCLK`), not a
2D fence. The display ISR (`0x0211d284`) handles `DINTRS` (`0x2178`) bit
2 only, enabled in `DINTRE` (`0x217C`) only while a flip is pending.
**`DINTRS` bits clear by writing 0** (Dell writes the status back with the
handled bit removed; 1s leave bits alone; confirmed on the device). Flips
are timed by polling the scan line **`DVLNUM` (`0x2308`)**, then writing
`GBBASE`/`VBBASE`.

**The interrupt line, measured (P, `rp-mbx` stage 4f, four runs).** With
`MINTENABLE` `0x800F` and `DINTRE` at 0, bit 0, bit 1 or bit 2 alone, each
event held 0.5 ms before being cleared by writing 0: all three bits set
again every time they were cleared (about 40 times in 40 ms each, i.e. at
every clear: far more often than once a frame; they look like conditions
or per-line events, not frame events), and **no GPIO followed them**
(GPIO32 toggled every ~16 µs in two phases: a clock, MMCLK's pin, also
busy while idle in other runs). `DVLNUM` advanced ~18 lines per 0.5 ms.
So no 2700G interrupt reached a PXA pin as tried. Still open: which GPIO
SYSINTR 27 is (needs the OAL), and what else `MINTENABLE`'s bits 0-3
select.

**The line is GPIO85, and it works (P, fifth run of 4e/4f, 2026-10-14).**
The OAL map (`interrupts.md`) named GPIO85. Found as an input, level 1;
claimed as a both-edge interrupt. With `MINTENABLE` `0x800F` and `DINTRE`
at bit 0, 1 or 2: **GPIO85 edged each time the enabled display event set
again after being cleared** (39-43 in 40 ms, the test's clear-and-hold
cadence); with `DINTRE` 0, none. With the MBX enables (`0x130` 0,
`0x87F5`, `0x400`) and 20 fills: none (as `0x12c` never sets). So: **the
display's events reach the PXA on GPIO85 (active low, likely); 2D work
never does.** The earlier runs saw GPIO85 low and still because their
uncleared events (cleared with 1s) held the line asserted between runs:
the 2700G isn't reset between images. Display bits 0-2 set again within
~0.5 ms of every clear, so they are not once-a-frame events as tested;
what each means, and whether `DINTRCNT` (`0x2180`, never touched by Dell)
sets a line for one, is the next question. `DVLNUM` advanced ~37 lines
per ms (~27 µs a line).

**Measured (P, `rp-mbx-blend` first run, 2026-10-14; log in

*The display's events.*
- **`DINTRS` is a plain read/write register.** The hardware sets bits on
  events, and a write stores the value written: a 0 clears a bit, a **1
  sets it**. Writing `!bit` read back `0x0007007E`, all the 1s written;
  writing `bit` read back that bit alone. So the only safe clear is Dell's:
  read the status, then write it back without the handled bit.
  **Correction:** the earlier finding that "bits 0-2 set again within
  0.5 ms of every clear" (`rp-mbx` 4f) was this. That stage cleared one bit
  by writing 1s to the others, which set them. E5 and B5 below repeat the
  mistake; run again with the fix (second run, below).
- **The frame:** lines 0-644 (645), 17,712 µs a frame (**56.46 Hz**),
  27.46 µs a line.
- **HBLNK0** (bit 0) sets once a line, 20-28 µs after a clear.
- **HBLNK1** (bit 1) and **VEVENT1** (bit 3) never set in 40 ms.
- **VEVENT0** (bit 2) sets once a frame, always on the line held in
  `DVECTRL`'s bits 16-27 (643 as found). Moved to 100 or 400, it sets on
  exactly that line (8 of 8 each).
- **With `DINTRE` bit 2 and `MINTENABLE` `0x800F`, GPIO85 interrupts once
  a frame at the chosen line** (5 in 100 ms, at lines 100 or 400). An
  interrupt at any scan line, so flips need no polling.
- **`DINTRCNT`** reads back what is written (1, 4) and **changes nothing
  measured** (second run, `local/rp-mbx-blend-run2.txt`): at 0, 1 and 4,
  HBLNK0 set 727-728 times in 20 ms (exactly once a line) and VEVENT0
  once. Left at 0.
- **Scan-out keeps up with heavy 2D work** (second run, B5): underrun
  and overrun bits stayed clear through 20 back-to-back full-screen fills
  (62 ms). The bits 4-6 found set at the start of that run were left by
  the first run's own writes.
- The second run repeated every other result of the first exactly.

*The 2D engine blends* (header bit 17 = "apply the blend state",
confirmed).
- **Blend word `[27:24]` is the destination factor, `[23:20]` the source
  factor.** result = source × Fs + destination × Fd, per channel, rounded
  to the destination's bits. The factor codes, measured with a coverage
  source (A = coverage / 15):

  | Code | Factor |
  |---|---|
  | 0 | 1 |
  | 1 | A |
  | 2 | 0 |
  | 3 | A (probably another alpha source that equals A here) |
  | 4-7 | 0 |
  | 8 | 0 |
  | 9 | 1 − A |
  | 10 | 1 |
  | 11 | 1 − A |
  | 12-15 | 1 |

  So bit 3 of a code inverts (1 − x), bit 2 forces 0, and bits 1-0 pick
  1, A, 0 or A. Dell's `0x09100000` = Fd 1 − A, Fs A: "over".
  `[31:28]` and bits 0-19 changed nothing here; they may matter with
  another alpha source.
- **The colour word is xRGB8888 when blending** (`0xF800` drew green,
  G = 0xF8). Bit 17 with blend word 0 adds the colour, saturating.
- **4 bpp coverage takes the high nibble first** (pixel 0 = bits 7-4).
  The blend is exact: blue to green within one step of the CPU's lerp at
  all 16 levels. The owner's photo shows the 16 steps.
- **Per-pixel alpha sources work.**
  - **Code 12** (32 bpp) is **ARGB8888**: red at alpha 0, ¼, ½, 1 over
    green gave `07e0 3de0 83e0 f800`, exact.
  - **Code 7** is **ARGB4444**: `07e0 45c0 8ba0 f800`, alpha 0, 4/15,
    8/15, 1.
  - Codes 13-15 act as 12.
  - Codes 8 and 9 read 1:5:5:5 colour with alpha 0.
  - Code 4 is unknown.
  - Without bit 17, codes 12 and 7 copy with format conversion to RGB565,
    ignoring alpha.
- **ADR-0022's "no ARGB blending in the 2D engine (likely hardware)" is
  wrong.** It was presumed from Dell never using it. Glass, ARGB images
  and translucent fills (a constant coverage tile) can be drawn by the 2D
  engine.
- **B4** (a fill with bit 17) blended the last source surface instead of
  its colour: with bit 17, the engine reads the source whatever the ROP.
- Engine stalls: none.

- **The CPU polling the fence doesn't slow the engine** (B8c): ten
  full-screen 32-bit fills landed after 61.8 ms polled without a pause
  (69,805 reads of the fence word), 62.2 ms polled every 1 ms, 65.0 ms
  every 5 ms (each at its polling's resolution). The engine's memory
  isn't held up by the CPU's reads; polling only costs the CPU's time.

**B9, measured (P, `RP_MBX_BLEND_B9`, X51v, 2026-10-22 night; logs
`local/rp-mbx-blend-B9-run1.txt`, `-run2.txt`; the gate's V15, P6, P7,
V3).** No stray writes (guard bands), no stall, state put back.
- **The clip rectangle** (`0x00000001`, right << 16 | left, bottom << 16 |
  top, header bit 18): a 64 x 64 fill clipped to (8, 8)-(24, 20) wrote x
  8-23, y 8-19: **right and bottom exclusive**, as a fill's end.
- **The scale word scales, nearest pixel, no filtering:** `0x60000000 |
  s << 18 | s << 4` with `s` = 32 x source / destination (`0x20` 1:1).
  A 16 x 16 source: 2x drew each pixel twice (columns 0 0 1 1 2 2 ...),
  0.5x every other (0 2 4 ...), 1.5x (0x15) 0 0 1 1 2 3 3 4 5 5 ...; no
  pixel a mix of two. Speed: a full-screen 2x upscale (240 x 320 32-bit
  to 480 x 640 RGB565) 18.7 ms, against 9.6 ms for the same copy 1:1 from
  a full-size source: **half speed per output pixel**.
- **8 bpp sources go through a palette** set by `0xC0000000, address`
  (256 32-bit entries in local memory): all 256 pixels exactly their
  entry (version 2); without the word, on an engine fresh from its reset,
  garbage (`0000`, `f83f`): the palette is needed. **Slow: a full-screen
  8 bpp copy 63.3 ms**, against 5.0 ms for a 16-bit copy.
- **1 bpp sources expand through palette entries 0 and 1** (not the colour
  word), **the high bit first**: `0xAA` bytes drew 1 0 1 0 ..., `0x0F` 0 0 0
  0 1 1 1 1.

**B10, measured (P, `RP_MBX_BLEND_B10`, X51v, 2026-10-22 night; log
`local/rp-mbx-blend-B10-run1.txt`; the gate's P13, V15, V17).**
- **Every raster operation is GDI's ROP3**: all 256 codes (in both bytes
  of the ROP4) gave exactly GDI's bitwise result on 32 bpp words, the
  colour word as the pattern, none stuck.
- **8 and 24 bpp fills** (formats `0x30000`, `0x58000`): 8 bytes of `A5`;
  24 bytes of `56 34 12` repeated (packed, blue first), nothing past.
- **Status bit 10 isn't "commands queued"**: with 130 words queued
  (`0x12c` = `0x00820000`, the FIFO level) it was clear, as after; its
  meaning is open.
- **Header bit 21 suppresses a fill's write too** (B7c: a copy's): 8
  pixels left as they were. Its purpose is open.

**The bus timing (`MSC1` CS3), `rp-cs3bus` 2026-10-19
(docs/research/memory-timing.md):** stepping CS3's strobe from Windows
Mobile's 17 clocks a beat to 14 sped flushes ~7% (33 -> 35 MB/s) and reads
not at all (12 MB/s): the 2700G paces the bus with RDY. At 13 clocks
(`RDF` 4) reads came back wrong (writes still right). A 60 s soak at 16
clocks: 0 misses.

**DMA into 2700G memory (open question 2), same run.** A full RGB565
screen (600 KiB) from SDRAM: the CPU copies it in **18.5 ms (33 MB/s)**;
the PXA27x DMA controller, memory to memory, in **20.0 ms (30 MB/s)**,
the copy intact, and the CPU kept **84%** of its idle pace meanwhile. The
bus to the 2700G, not the copier, sets the speed; DMA's gain is the CPU
time it gives back.

**The game writes the 3D core's registers itself.** No request is sent per
frame: `eglSwapBuffers` only flushes the open scene and waits in `Sleep`
loops. GLES has a write-register helper (`0x02270708`: store value at
base + offset) and a read helper (`0x0226f488`), and `0x0226f4a0(base,
count, table)` writes `count` (register, value) pairs through it: 9-pair
tables from the scene routine (`0x0225e8f8`, called from `glDrawArrays`,
`glDrawElements`, `glClear`, `glEnable`, `glScissor`, `eglMakeCurrent`...)
and from `0x022611ac`; 4- and 2-pair tables elsewhere. So Dell's driver
maps the register window where the game can write it (it imports
`VirtualCopy`), and the escapes only set things up (the device, contexts,
2700G memory, render targets). For RetroPane this means a render is
started by a list of register writes, which a test image can make directly.

**Where the register window comes from.** `eglInitialize` (`0x02261444`)
sends 102000 and gets a count and 44-byte device entries (type at `+4`: 0
or 1; an id at `+8`); 102001 opens each (type 0 into the GLES device at
`+4`, type 1 at `+20`). 102001's reply holds a pointer (`+8`) to **Dell's
own device structure** (the 0x180-byte one that keeps the five mapped
regions, `0x0211be7c`), which the game then reads directly (`0x02270ee0`):
its `+0x2c` becomes the **register base** the game writes through
(`device + 36`), with `+0x88` beside it and, for device types 1-2, the
addresses of Dell's fields `+0x164`, `+0x168`, `+0x16c` (likely the
counters that sync the CPU with the hardware). The game and the display
driver share that structure. 102001 (the first connection) reaches
`InterruptInitialize` in Dell's driver: the interrupt thread starts then.
102012 (at `eglInitialize`) reaches `VirtualAlloc` and
`VirtualSetAttributes` but not `VirtualCopy`: ordinary memory with changed
caching, likely a buffer the CPU and the core share. The exact job of each
memory request (102003, 102004, 102012, 102013) is left to M2/M3.

**Rendering is two-stage, as in every PowerVR: the tile accelerator, then
the 3D stage.** The GLES context holds two register tables, both written

## The scene bytes (ADR-0024 M2, static analysis, 2026-10-14, in progress)

**Route.** A first triangle doesn't need the tile accelerator: Dell's own
2D fills draw through the 3D stage alone, with the CPU writing the
per-tile object lists and starting only the 3D table (`0x680`). That path
is proven on this chip (WM's fills), so M2 decodes it first; the TA path
(vertex words fed to the TA, for fast GLES) comes after. The words match
the **Dreamcast PowerVR2's published object list and parameter formats**
closely (KallistiOS and the PowerVR2 documentation are public), which is
the decoding guide; Dell's code confirms or corrects each word.

**A minimal scene, written whole by `0x021178b8` (A):**

| Word(s) | Value | PowerVR2 reading |
|---|---|---|
| object list `+0` | `0x40800000 \| (params + 64) / 4` | triangle-strip pointer: bit 31 0 (strip), mask bit 30 (triangle 0 drawn), bits 23-21 skip = 4, bits 20-0 the parameters' offset in words |
| `+4` | `0xF0000000` | end of the object list |
| `+8` to `+63` | 0 | (14 words) |
| params `+0` | `0xE0000000` | ISP word: depth compare bits 31-29 = 7, "always" |
| `+4` | `0x22200E80` | TSP word: blending, shading (to decode) |
| then | 4096.0, 4097.0, 4096.0, 4096.0, 4097.0, 4096.0 | three vertices' x, y (floats; 4096 likely a coordinate bias) |
| then | 1.0 six times | depth / 1/w per vertex (two words each, or z then a second value: to settle) |
| then | 0, 0, 0 | colours |

The 2D engine's 32-bit address range shows here too: the end of the
parameters is kept masked to 32 MiB (`& 0x01FFFFFC`), as measured for the
2D engine.

**Dell's rectangle slots (`0x02117d9c`, from `0x02118080`):** 32 objects of
52 bytes, each addressed by an object-list word `0x60200000 \| offset / 4`
(a strip pointer, mask bits 30 and 29 = two triangles: a rectangle);
variants `0x612001DC` and `0x60A00208` (bit 24 set; bit 23 set: flags to
decode). Each object begins with a TSP-like word (`0x22206F80` /
`0x22207F80`), then vertex floats (4096.0 again).

**The region array (A, `0x0211a810`-`0x0211a8b4`), decoded.** Two words
per tile, rows outer, columns inner: `x | y << 8` (each `& 127`), then the
object list's address (`& 0x01FFFFFC`). The last entry gets bit 31. Dell
points every tile at the same object list.

**That object list (`0x0211a8e8`-`0x0211a924`):** strip pointers
`0x41800000 | offset / 4` to objects 176 bytes apart, then `0xF0000000`.
Each object's parameters start `0xE0000000` (ISP), `0x22200E80` (TSP), 0,
then floats (2048.0 = `0x45000000`, 1.0).

**So the 3D stage reads three structures:** the region array (one entry
per tile, address in register `0x608`), the object lists it points to
(strip pointers, then the end word) and the objects' parameters (ISP word,
TSP word, then float vertices; the parameter buffer in `0x60C`), with the
tile grid in `0x654`/`0x658` and the render target in `0x650`/`0x660`.

**An object's 15 words after ISP and TSP (A, both of Dell's 17-word
objects lined up):**

| Words | Minimal scene (`0x021178b8`) | Background (`0x0211a930`) | Reading |
|---|---|---|---|
| 6 floats | (4096, 4097), (4096, 4096), (4097, 4096) | (0, 0), (2048, 0), (0, 2048) | x, y of the three vertices |
| 3 floats | 1.0 x 3 | 0 x 3 | z per vertex |
| 3 floats | 1.0 x 3 | 1.0 x 3 | 1/w per vertex |
| 3 words | 0 x 3 | 0 x 3 | colour per vertex (ARGB) |

Vertices are stored grouped (all x/y pairs, then all z, then all 1/w,
then all colours), as the 2026-10-13 note found for four-vertex objects.
The background triangle (0, 0)-(2048, 0)-(0, 2048) covers the screen: the
usual way to clear. Dell's quick rectangles use a shorter 13-word form
(not needed yet).

helper, `0x0211b5b4`-`0x0211b770`; the "15-pair table"), stored at the

| `0x610` | 0 |

## The 3D core's interrupt, filtering, mipmaps and texture formats (static analysis, 2026-10-15)

From Dell's driver (`local/re/ddi_2700g/full.asm`) and the GLES driver
(`local/re/gles/libGLES_CL.asm`, its data read from the DLL). Every claim
is (A) static until a device run confirms it; ADR-0026 has the plan.

**Interrupts (Dell's driver).**
- SYSINTR 27 is GPIO85 alone (`interrupts.md`), and one thread
  (`0x0211d440`) serves it: it writes `MINTENABLE` (system `+0x18`)
  `0x000F` (handlers running), walks a list of handlers, calls
  `InterruptDone`, writes `0x800F`. Those are the only values Dell ever
  writes there (10 call sites); it never reads or writes `MINTSTAT`
  (`0x1C`), `SINTENABLE` (`0x20`) or `SINTSTAT` (`0x24`).
- One handler (`0x021192b4`) serves both the MBX core and the display,
  through accessors that pick `0x12C`/`0x130`/`0x134` (MBX) or
  `0x178`/`0x17C` (the display's `DINTRS`/`DINTRE`): it reads the enable,
  **writes it back with the low 16 bits cleared** (masking every source
  while it runs), reads the status, handles `status & saved enable` (bits
  5, 10, 4, 2, 6, 7, 8, 9), clears each through `0x134` (bit 2 together
  with bit 3: `0x0C`), and ORs the saved enable back afterwards.
- Dell's set-up (`0x02118784`-`0x021187ec`) masks all (`0x130 &=
  ~0xFFFF`), clears all (`0x134 = 0xFFFF`), then sets **`0x130 = 0x87F5`**:
  bits 0, 2, 4-10 and **15**.
- Why `rp-mbx3d` version 20 (T2) saw no edge: it ran after a core reset,
  which leaves `0x130`'s low 16 bits clear, and enabled bit 2 alone.
  **Bit 15 is likely the MBX core's master interrupt enable**, as bit 15
  is `MINTENABLE`'s; and any other enabled, uncleared status bit holds
  GPIO85 asserted so no edge shows (as found for the display's events).

**Texture filtering and mipmaps (GLES driver).**
- `glTexParameter` (`0x022633b8`): `GL_TEXTURE_WRAP_S/T` go straight into
  TEX0 bits 31-30 / 29-28 (repeat 0, clamp 2: as measured, version 22);
  `GL_TEXTURE_MAG_FILTER` linear stores `0x80000000`, nearest 0;
  `GL_TEXTURE_MIN_FILTER` stores nearest 0, linear `0x80000000`,
  nearest-mipmap-nearest `0x20000000`, linear-mipmap-nearest
  `0xA0000000`, nearest-mipmap-linear `0x40000000`, linear-mipmap-linear
  `0xC0000000`.
- The per-unit words (`0x02267434`): **TEX1 = address / 128 (bits 24-0) |
  a level-of-detail value in bits 28-25 (computed in floats from the
  texture's levels) | the mag and min filter words**. So filtering lives
  in **TEX1 bits 31-29**: bit 31 linear, bits 30-29 the mipmap mode.
  Dell's `0x0E000000` (ours since version 21) is point sampling with LOD
  7; DoomGLES's `0xCE000000` is linear-mipmap-linear with LOD 7.
- Where the levels sit in memory is decided at upload (`0x022656b4`), not
  read in this pass: the device test tries both orders.

**Texture formats (GLES driver's table at `0x0225D310`).** Rows of (bits a
texel or block, TEX0 format word, components). The format field is
**TEX0 bits 17-13** (wider than the 3 bits measured in version 18):
`0x0000` ARGB1555, `0x4000` RGB565, `0x8000` ARGB4444, `0x10000` (code 8,
16-bit, two components: luminance-alpha, likely), `0x14000` (code 10,
8-bit: luminance or alpha), **`0x18000` (code 12): 32-bit texels** (the
RGBA8888 and RGB888 rows), **`0x38000` (code 28): PVRTC 4 bpp**,
**`0x20000` (code 16): PVRTC 2 bpp** (`glCompressedTexImage2D` accepts
`0x8C00`-`0x8C03`, RGB and RGBA of each, in 64-bit blocks; the paletted
`0x8B90`-`0x8B99` are expanded by the driver into 565/4444/1555/8888).

## Depth buffers, mipmap levels and the target format (static analysis, 2026-10-15, after `rp-mbx3d` version 24)

From the GLES driver (`local/re/gles/libGLES_CL.asm`). (A) until
`rp-mbx3d` version 25 runs.

- **The per-frame register list** (built at `0x022616dc`, patched by the
  scene routine `0x0225e5c4`): `0x610` = `(n - 1) << 7` with a depth
  buffer (`n` from the surface, likely its tiles; the frame adds bit 1
  store, bit 0 load), `0x30001` without; `0x614`/`0x618` `0x1E3CE508`;
  `0x61C` `0x00020007`; `0x644` 0; **`0x648` 1**; `0x64C` 0; **`0x650` the
  target format** (6 for 32-bit as Dell's table; 1 and 3 for two other
  surface formats, 16-bit likely: the T4 question); `0x654`/`0x658` the
  size; `0x65C` the target; `0x660` stride / 4; **`0x674` the depth
  buffer** (an address from the EGL surface, allocated outside the GLES
  driver: its size and alignment not read); **`0x6D0` 1**; `0x6DC` 1
  (then the clear depth); `0x860` the grid; `0x60C`; `0x680` start.
  Version 24 set `0x674` and `0x610` on Dell's table, without `0x648`,
  `0x6D0` and the rest: nothing was stored.
- **TEX0 bits 12-9: the mipmap level value.** The upload (`0x0226576c`)
  builds TEX0 as the kept bits, the size codes, the format (bits 17-14 of
  its table word), then **`0xB << 9` for a texture without levels**, or its
  level value `<< 9` with levels (DoomGLES's `0x...9600` has the `0xB`).
  Version 24 left them 0: no level drew. TEX1 bits 28-25 are a bias
  computed in floats ((bias clamped to -0.4375..2, + 1.75) x 4), not a
  level selector. Where the levels sit in memory is decided in a copy
  helper (`0x02266c60`), not read.

**`rp-mbx3d` version 25 on the device (2026-10-15,
`local/rp-mbx3d-run25.txt`).**

- **T12b, mipmaps: work.** With TEX0 bits 12-9 non-zero (3, 6, 7 or
  `0xB`: all alike) and TEX1 nearest-mipmap (bit 29), **layout B** (the
  base first, each level after the larger one) drew the 16 x 16 level on a
  16 px quad and the 8 x 8 on an 8 px quad (a 64 x 64 texture); layout A
  (the PowerVR2's, smallest first) always drew the base. Version 24 left
  bits 12-9 at 0 and drew only the base: **bits 12-9 are the highest level
  index allowed**.
- **T13b, PVRTC's block order: twiddled like texels** (x in the odd bits):
  each block's centre showed row 0 = blocks 0, 2, 8, 10, row 1 = 1, 3, 9,
  11. Both models had assumed it; now measured.
- **T11b, depth stored across renders: still nothing** with the GLES
  driver's full register set (`0x648`, `0x6D0`, the rest), `n` 16 or
  2400, load bit on or off: the buffer untouched, B drew everywhere. The
  GLES scene routine (`0x0225e5c4`), with a depth buffer, also sets **bit
  19 of the tile accelerator's configuration word** (`0x85C`, ours never
  written on the direct path) and `0x610`'s store bit: depth storage may
  belong to the TA path. **Parked** until the TA path is built for games
  (ADR-0026 D7); then one try with `0x85C` bit 19 settles it. The
  interface doesn't need it (each render's depth starts from the
  background).

## Alpha test, fog, the second texture unit (static analysis, 2026-10-18)

Read from Intel's `libGLES_CL.dll` (ROM A08) because three owned games
use these features and DoomGLES didn't: Call of Duty 2 (`glAlphaFuncx`,
`glFogx`, two texture units, a `GL_LUMINANCE` texture), THPS2 (fog),

`+0xF4`, the second word (called "ISP" so far) at `+0xF8`, the enable
flags at `+0x144` (`glEnable`: bit 0 `GL_BLEND`, bit 1 `GL_ALPHA_TEST`,

| Finding | Confidence | Evidence |
|---|---|---|
| **The second state word's top 11 bits are the alpha test**: bits 31-29 the comparison in GL order (`GL_NEVER` 0 ... `GL_ALWAYS` 7), bits 28-21 the reference (0-255). `glAlphaFuncx` stores `func << 29 \| ref << 21` at `+0x5E8`; the builder ORs it over the word's low 21 bits. Dell's objects' `0xE0000000` = "always, reference 0"; DoomGLES's `0xEC800000` = "always, reference 100" | **confirmed** (device, `rp-glesfeat` A) | `glAlphaFuncx` `0x02262060`; builder `0x0226770C` |

| **Fog = TSP bits 25-24**: bit 25 alone (every captured word: Dell's `0x22220E80`, DoomGLES's `0x22640200`) = no fog; `GL_FOG` on sets **bit 24 instead**; the logic-op path sets neither | likely (code) | `0x022677B8` |

## The MBX cores' clock (static analysis, 2026-10-15)

From Linux mbxfb's register definitions (`local/re/mbxfb_reg_bits.h`,
`mbxfb.c`) and Dell's driver (`local/re/ddi_2700g/full.asm`). (A) until
`rp-mbx3d` version 26 runs.

- **`MBXCLK` bits 3-2 divide the MBX cores' clock** (0 by 1, 1 by 2, 2 by
  3, 3 by 4; bits 1-0 the enable). **Windows Mobile's `0x5` is divide by
  2.** The cores' clock is SYSCLK / divider; `SYSCLKSRC` is 2 under WM
  (Linux's `SYSCLKSRC_PLL_2`: the core PLL, likely); the PLLs give
  `13 MHz x M / (N x 2^P)` (`COREPLL` `0x038`, `DISPPLL` `0x03C`: M bits
  12-7, N 6-4, P 3-1), set by WM's boot code (Dell's driver never writes
  them) and never read yet.
- **Dell's driver picks the divider** (`0x021204f8`-`0x0212056c`): the
  system clock from its `CoreClock` registry setting (a PLL search around
  `0x0211f980`; literals 47, 66, 99/100, 121 and 133 MHz nearby), then for
  both `MBXCLK` and `M24CLK` the smallest divider from 2 to 4 keeping the
  clock **at or under 75 MHz** (`0x047868C0`, `0x02120724`); 1 if the
  system clock is already under it. So divide-by-2 is Dell's cap at work:
  the system clock lies between 75 and 150 MHz, and the cores run at half
  of it. Whether 75 MHz is the chip's rating or Dell's margin is not in
  the code. Linux mbxfb sets the core PLL to ~71.5 MHz and `MBXCLK` to
  `0x1` (divide by 1, 2D only).

**`rp-mbx3d` version 26 on the device (2026-10-15,
`local/rp-mbx3d-run26.txt`).**

- **S26a, the cores are clock-bound.** At `MBXCLK` divide by 2, 3 and 4:
  2400 tiles 12,484 / 18,724 / 24,968 us, 600 tiles 3,132 / 4,692 / 6,256
  us, a full-screen 2D fill 6,180 / 9,268 / 12,360 us: **exactly in
  proportion to the divider**, 3D and 2D alike. Every MHz of the cores'
  clock is speed.
- **S26c, the clocks:** `COREPLL` `0xBB1` = 13 MHz x 23 / 3 = **99.67 MHz**
  (mbxfb's own "100 MHz" setting), `DISPPLL` `0xEC5` = 23.56 MHz (the
  pixel clock), `PLLSTAT` 7 (both locked), `SYSCLKSRC` 2, `MEMCLK` 1,
  `M24CLK` 2. So **Windows Mobile runs the MBX cores at 49.8 MHz**, a
  third under the 75 MHz Dell's driver allows them; **Dell's default
  "CoreClock" is 133 MHz** (`0x021220f4`), which at divide by 2 gives 66.5
  MHz. Dell's driver sets the PXA's bus timing (`MSC1`) for the 2700G by
  the same clock: one setting for 99 MHz and up, which 133 MHz shares.
  Next: the core PLL stepped up, `rp-mbx3d` version 27.
- **S26b (T4), a 16-bit target: works.** `0x650` 1 wrote RGB565 (red
  `0xF800`, green `0x07E0`, blue `0x001F`, white `0xFFFF`), 3 wrote
  ARGB1555 with the alpha bit set (`0xFC00`, `0x83E0`, `0x801F`); tiles
  stay 8 x 16; **`0x660` is the stride in bytes / 4** in every format (240
  for 960 bytes; 480 skipped every other line). The 16-tile block took 120
  us, no faster than 32 bits as measured (a cost per tile, not per
  byte). Built: `PixelFormat` on the renderer's `Picture` (both models
  write 16-bit targets as measured). The interface's screen pictures stay
  32-bit (ADR-0023's choice, for exact 2D blending and dithering); making
  them RGB565 is an ADR-0023 change for the owner (half the memory and
  bus traffic of every picture; the 2D engine's blends onto 565 need
  their own device check).
## The MVED1 video decoder (static analysis, 2026-10-14)

Sources: `pvrvadd.dll` (16 KiB, the hardware layer: 30 `M24VA_*` decoder
and 9 `VDISP_*` overlay functions) and `wmv9decoder2700G.dll` (173 KiB, a
DirectShow Media Object that uses it), both from the A08 ROM (A), plus
`ddi_2700g.dll` for the parts behind its escapes. The decoder DLL is
byte-identical in all four ROM copies; `pvrvadd.dll` differs between ROMs
(not compared further). **`wmv9decoder2700G.dll` is UPX 3.02-packed**
(LZMA, an ARM call filter, relocations stored byte-swapped): it was
unpacked locally with a small script before disassembly (`local/re/mved/`,
never committed). Disassembled with `llvm-objdump`, labelled by a copy of
`local/re/gles-scripts/annotate.py` that also reads `ldr rX, [pc]`
literals. Findings only; no code copied. "M24" is the name the drivers and
Linux's `M24CLK` give this unit.

**Shape.** `pvrvadd.dll` reaches the hardware the way the GLES library
does: escapes to Dell's display driver set things up (open the device,
2700G memory, the clock), then the library writes the decoder's registers
and command windows itself, through mappings the display driver shares.
The decoder DLL is the codec: it parses the bitstream on the CPU and feeds
the chip a stream of macroblock commands. No interrupt is used: completion
is a status register the library polls.

### Registers (offsets from `0x0FFE3000`)

Every offset `pvrvadd.dll` touches. **It reads only `0x50`, `0x80` and
`0xA0`** (the bus-hang rule: read nothing else). Addresses are byte
offsets in 2700G local memory (as for the 2D engine), always written
**divided by 8**. Sizes are in pixels, strides in bytes.

|---|---|---|---|---|

| `0x14` | W | frame address / 8 | **reference frame 1** (forward; the only one the WMV9 decoder sets) | confirmed (A) |
| `0x18` | W | frame address / 8 | reference frame 2 (backward; never set by this decoder) | likely |

| `0x34` | W | destination / 8 | conversion destination, mode 1 | confirmed (A) |
| `0x38` | W | `width \| height << 11` | conversion size | confirmed (A) |
| `0x3C` | W | mode 1: `(destination stride / 4) << 9 \| source stride / 8`; mode 3: source stride / 8 | conversion strides | confirmed (A) |

| `0x88` | W | the bits handled; 3 at reset | **acknowledge** status bits (1s clear) | confirmed (A) |
| `0x90` | W | 0 or 1 | 1 = the chip does the inverse transform (coefficient mode, below); 0 = the CPU sends residuals | confirmed (A) |

**Sequences (A).** All run under a lock word shared with Dell's driver
(`+0xB0` of the structure Dell returns at connect, taken by
compare-and-swap with the process id). Every `M24VA_*` call fails with
"lost" (5) while that structure's `+0x80` is set (most likely Dell's
power-down flag); initialisation clears it after the reset.
`M24VA_GetSlavePortStats` and `M24VA_GetStats` only return zeros and the
`M24VA_SimScript*` functions are empty: a simulator hook compiled out.

1. **Reset:** `0x00` = 1, `0x00` = 0, `0x88` = 3; the library's window
   indexes go back to 0.
2. **Frame set-up** (once per stream): `0x20` = size. Frames are allocated
   in 2700G memory (escape 102003, 4 KiB aligned).
3. **Begin a frame:** wait until the display has finished with the output
   frame (a counter pair in Dell's surface record; 10 ms sleeps), then
   `0x90` = coefficient mode, `0x10` = output, `0x24` = stride, `0x14` =
   reference. Once per session the command word `0x1A800000` follows (a
   chroma position word for macroblock 0, 0; below).
4. **Feed commands** (below). The library stages up to 31 words and
   writes them when the FIFO has room: it reads `0x50`; with no room it
   polls 100 times, sleeps 1 ms, and gives up after 10 tries ("timeout", 7).
5. **End the frame:** command `0x78000000`; when the caller waits, poll
   `0x80` until bit 1 is set (100 reads, then a 1 ms sleep, 10 tries), then
   write 2 to `0x88`.
6. **Convert** (`M24VA_FrameConvert`, optional): finish the frame, set
   `0x30`-`0x44`, then `0x48` = mode; done is `0x80` bit 0, acknowledged
   with 1.

### The command stream (`M24VA_WriteMCCmdData` / `M24VA_WriteMCCmdBlock`)

Words go to the first window; a "block" is just several words in a row.
The top four bits name the word. As found in the WMV9 decoder's
macroblock routines (`0x1000f734`-`0x1000fe9c`, `0x100123a0`-`0x10012630`):

| Word | Meaning | Confidence |
|---|---|---|
| `0x00000xxx` | **prediction set-up** for what follows: bits 1-0 the plane (0 luma, 1 chroma), bit 2 / bit 3 width 8 / 16, bit 4 / bit 5 height 8 / 16 (`0x28` a 16 × 16 luma macroblock, `0x15` an 8 × 8 chroma block), bit 6 and bits 9-8 flags from the vector mode, bit 10 a second vector follows | fields confirmed (A); flag meanings a guess |
| `0x080000xx` | **prediction block select**: bit 6 right half, bit 4 lower half (which 8 × 8 quarter, with four vectors a macroblock) | likely |
| `0x80000000 \| 1 << 30 \| y << 14 \| x` | **motion vector**, two signed 14-bit fields (x in bits 13-0, y in 27-14). The decoder adds 32 for the right or lower 8 × 8 block, so it is relative to the macroblock, most likely in quarter pixels; halved first when the stream uses half-pixel vectors | likely (units: device test) |
| `0x80000000 \| y << 14 \| x` (bit 30 clear) | the second vector of a two-vector prediction (only after a set-up with bit 10) | likely |
| `0x18000000 \| position` | **where the macroblock goes**: luma `0x1D000000 \| (row × 16) << 11 \| column × 16`, chroma `0x1A800000 \| (row × 8) << 11 \| column × 8` (row and column in macroblocks) | likely (bits 26-23 may be a size code rather than part of the position) |
| `0x10000xxx` | **residual block header**, before that block's data: bits 3-2 the block's x within the macroblock in 4-pixel steps, bits 5-4 its y, bits 9-8 the transform size (0 8 × 8, 1 4 × 8, 2 8 × 4, 3 4 × 4, WMV9's numbering), bit 1 intra (no prediction to add); one inter-frame path also sets bit 7 | fields confirmed (A); bit 7 a guess |
| `0x78000000` | end of frame (the frame-done status follows) | confirmed (A) |

A typical inter macroblock: set-up `0x28`, position, then for each
predicted block `set-up, 0x08000000 | block, vector` (three words: the
"MC command block"), then per coded block a header and its data in the
second window. An intra macroblock: set-up with no vector, then per block
a header with bit 1 and its coefficients.

| Work | Where | Evidence |
|---|---|---|

**Completion:** polled. `pvrvadd.dll` imports nothing for interrupts; done
is `0x80` bit 1 (frame) or bit 0 (conversion), acknowledged in `0x88`.
Whether the unit can raise the 2700G's interrupt line (GPIO85, through
`MINTENABLE`) is unknown.

**Formats.** The decoder object registers for WMV1, WMV2, WMV3 (WMV9),
WMVA, WMVP and WVP2 (WMV9 screen and image), and MP42, MP43 and MP4S
(Microsoft's MPEG-4 variants), with outputs YV12, I420/IYUV, YUY2 and UYVY
(format codes in the image). The chip path was followed in the WMV9

and MPEG-2** if its 8 × 8 transform is the MPEG one (IEEE 1180), or
switchable to it, rather than only WMV9's integer transform. That is the
first thing the device test measures (ADR-0025). H.264 is out of reach
either way (different transforms, intra prediction and deblocking).

**Left open (for the device test, ADR-0025):** what `0xA0`'s two bits

the transform's exact arithmetic; which scan each `0x8000` mode selects;
reset timing; how fast a frame decodes.

- **The system clock is also the local SDRAM's clock.** Dell's timing
  routine (`0x0211fb98`) turns the SDRAM table's nanoseconds into cycles at
  the system clock for **`LMTIM`** (`0x1018`; tRAS raised so tRAS + tRP >=
  tRC), sets **`LMREFRESH`** (`0x101C`) from the refresh period, and picks
  **`LMTYPE`**'s (`0x1014`) CAS latency by clock: CL1, CL2 at or above the
  table's first threshold, CL3 at or above its second.
- **Dell keeps ten SDRAM tables** (`0x0213F93C` on, 14 words each:
  thresholds, timings in ns, refresh 64 ms, **a maximum clock**), chosen
  by the `SDRAMMemType` registry value; **CoreClock is clamped to the
  table's maximum** (`0x02122334`).
- **The X51v's is the first** (`0x0213F93C`): CL2 from 50 MHz, CL3 from
  100 MHz, tRAS 48, tRP 25, tRCD 25, tRC 85 ns, **maximum 100 MHz**. It is
  the only table that gives what WM leaves: at 99.67 MHz tRC 9, tRP 3,
  tRCD 3, tRAS 9 - 3 + 1 = 7 (`LMTIM` `0x73392`), CL2 (`LMTYPE` `0xAC8`).
  So Dell's default 133 MHz CoreClock is clamped to 100, and the PLL search
  lands on 99.67 MHz: **the local memory is at its rated maximum now.**
- Consequences: raising `COREPLL` overclocks the local memory (and CL2 at
  133 MHz is out of any SDRAM's spec). Within Dell's limits (memory <= 100
  MHz, MBX cores <= 75 MHz) the faster MBX setting is a **75 MHz system
  clock with `MBXCLK` divide by 1**: the cores 50% faster, the memory 25%
  slower, and the PXA's bus timing in Dell's slower tier (25-99 MHz:
  `0x79D4`/`0x7DF1` against `0x2484`/`0x2481`), which slows the CPU's
  writes into 2700G memory. Dell's own divider logic picks exactly this
  for a 75 MHz CoreClock.

## Plane composition (spec, 2026-10-12)

Register layouts from (B), the `mbxfb` header and its overlay, plane-order
and alpha ioctls; meanings marked **assumed** are what the emulator models
until `rp-blend` checks them on the device.

| Register | Offset | Fields | Confidence |
|---|---|---|---|
| `VOVRCLK` | 0x0044 | `[0]` video overlay clock enable; mbxfb sets it with the stream | likely; the model shows no video plane without it |
| `VSCTRL` | 0x2004 | `[30:27]` format (9 planar YUV, 0xC UYVY, 0xD VYUY, 0xE YUYV, 0xF YVYU), `[26]` gamma, `[25]` colour conversion (YUV to RGB), `[22]` co-sited chroma, `[21:11]` width − 1, `[10:0]` height − 1 | confirmed (names) |

Rules learned from mbxfb's code: chroma planes have half the Y stride (its
U/V stride is `(width / 2 + 7) & ~7` with a Y stride of `(width + 15) &
~15`); **write `VUBASE`/`VVBASE` before switching `VSCTRL` to a planar
format**, or the chip hangs until reset (mbxfb's own comment).

Windows Mobile's state (rp-probe, 2026-10-11): graphics in slot 0, opaque;
`VSCADR = 0x01000000` (video off, slot 1: WM puts video **above** its
desktop); `VSCTRL = 0x0600780F` (16 × 16, gamma and conversion on).

**The mixing rule** (what the emulator and `rp_drv_mbx_display::scanout`
both compute, bit for bit; the device's exact arithmetic is unknown):
each plane pixel becomes 8-bit `(r, g, b, a)` (ARGB4444 channels × 17,
ARGB1555 alpha 0 or 255, RGB565 shifted up without bit replication, other
formats opaque; YUV through BT.601 studio range: `c = Y − 16, d = U − 128,
e = V − 128`, `R = (298c + 409e + 128) >> 8`, `G = (298c − 100d − 208e +
128) >> 8`, `B = (298c + 516d + 128) >> 8`, clamped). Starting from
`BGCOLOR`, planes are mixed from slot 0 up (graphics before video in one
slot): `out = (src·k + out·(255 − k) + 127) / 255`, with `k` = 255 (none),
`a` (per-pixel), `255 − a` (inverse, **assumed**) or the global alpha. The
screen size is the display-enable window (`DHDET`/`DVDET`).

RetroPane's use: wallpaper in the video plane, slot 0, opaque (4:2:0: 450
KiB for 480 × 640, and what a JPEG decodes to); interface in the graphics
plane, slot 1, per-pixel alpha (ARGB4444, ordered dither, 600 KiB). Every program takes
the screen with `Display::adopt`, which switches the video plane and
cursor off, so no layer a previous program left can hide its screen.

**Measured on the owner's X51v** (`rp-blend`, 2026-10-12, three runs,
photos and run logs):

| Finding | Confidence | Evidence |
|---|---|---|
