# The emulator and the real hardware

The emulator (`Drakey83/retropane-qemu`, a QEMU fork with X51v models) is
only useful while it behaves like the device. **Rule:** every fact learned
on the real X51v that a model could reproduce goes into the fork, with a
test in `cargo xtask emu` that fails without it; what can't be modelled is
listed here with the reason, so nobody trusts the emulator for it. Each row
names the finding, where it is written up, and the emulator's state.

## How to add a row

1. Record the fact in the block's spec (`docs/hw/<block>.md`) with its
   evidence, as always (`CLEANROOM.md`).
2. If a model can reproduce it: change the fork, add or extend an emulator
   boot in `xtask/src/emu.rs` that fails without the change, tag a release
   (`rp-vX.Y.0`), bump `QEMU_RELEASE` in `xtask/src/emu.rs`, re-record the
   bench baseline (`cargo xtask bench --update`: baselines are tied to the
   emulator version), and run the suite on the **released** build for this
   platform too (`RETROPANE_QEMU=release cargo xtask emu`: on Windows that
   is the native build contributors download, which the local WSL build and
   Linux CI don't cover; item 61 hid there for two releases).
3. Add the row here either way.

## Known emulator issues

- **Windows release only: no second enumeration after the loader's
  reconnect** (rp-v0.15.0, rp-v0.16.0 and rp-v0.17.0; Linux CI and the WSL
  build of the same tag pass). It fails every check where an image runs
  under the loader over USB and returns: `emu-usb`, `emu-trace` (also on
  rp-v0.16.0) and `emu-drive`. An earlier note said the Windows release
  passed everything else; that was never run, because `cargo xtask emu`
  stops at its first failure (2026-10-16: run one by one, `emu-stale`,
  `emu-fullsize`, `emu-storfast` and, after two harness fixes, `emu-cf`
  pass). `RETROPANE_QEMU=release cargo xtask emu-usb`: the image goes
  in over USB (SHA-256 matches), runs, and the loader prints its run log and
  `RPLOAD1 READY` on the serial line, but nothing arrives on the USB socket.
  With `-d guest_errors,unimp` the UDC model logs "enumerated and configured"
  once on Windows and twice on WSL, and logs no "host gave up" on Windows: the
  host's second attach never runs its script. The loader's reconnect is a
  plain `UDCCR.UDE` off/on (`drivers/pxa-udc` `disable`/`enable`), which the
  model turns into `H_IDLE` then `H_ATTACH` plus a `QEMU_CLOCK_VIRTUAL` timer.
  So on the Windows build either that timer never fires or the UDE write is
  missed. Next step: a Windows debug build of the fork with a log line in
  `udc_write`'s UDE path and in `host_step`. The `0x58000000` (IMPMCR) invalid
  read in the log is `diag`'s register dump and appears on both builds.
