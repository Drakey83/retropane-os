# The emulator and the real hardware

The emulator (`Drakey83/retropane-qemu`, a QEMU fork with X51v models) is
only useful while it behaves like the device. **Rule:** every fact learned
on the real X51v that a model could reproduce goes into the fork, with a
test in `cargo xtask emu` that fails without it; what can't be modelled is
listed here with the reason, so nobody trusts the emulator for it. Each row
names the finding, where it is written up, and the emulator's state.

| The CPLD's registers don't read back; the backlight enable is `0x18` bit 2 (2026-10-12) | `cpld.md` | Modelled (rp-v0.11.0): writes go to latches that never read back; reads return the status values measured with Windows Mobile's state (`00=0048 04=00a0 06=0002 14=0002`, `0x04` bit 1 set with no CF card; `0x1E` the LCD type while latch bit 3 is set). | The MBX 2D engine: command window at `0x0FFF5000` (sequential words, wrapping at 4 KiB), FIFO level in `0x12c`, solid fills (RGB565, 32 bpp, end exclusive, colour in the low bits), the fence (2026-10-13; confirmed on the device by `rp-mbx`: 3.1 ms per full-screen fill) | `2700g.md` "The MBX 2D engine" | Modelled (rp-v0.12.0): fills run the moment their last word arrives (so the FIFO always reads empty and fences land at once: timings are not modelled); other 2D operations are logged as unimplemented. Copies (rp-v0.12.0): clipped, colour-keyed, pixel by pixel, rows always top down (bit 23 has no effect, as measured on the device 2026-10-14) and right to left with bit 24, so an overlap copied the wrong way smears as on the chip. The engine's address map as measured 2026-10-14: 32 MiB decoded and wrapping, reads at 16-31 MiB return `0x1000008C` in every word, 32 MiB mirrors 0. **Not known, so not modelled:** engine writes past 16 MiB (dropped and logged), whether consecutive commands can overlap in time, and how fast anything is (fills, copies and DMA all finish at once here). `cargo xtask emu-mbx` checks the image's own read-backs and the GPU-drawn picture pixel by pixel; skipped on older emulator releases |

## How to add a row

1. Record the fact in the block's spec (`docs/hw/<block>.md`) with its
   evidence, as always (`CLEANROOM.md`).
2. If a model can reproduce it: change the fork, add or extend an emulator
   boot in `xtask/src/emu.rs` that fails without the change, tag a release
   (`rp-vX.Y.0`), bump `QEMU_RELEASE` in `xtask/src/emu.rs`, re-record the
   bench baseline (`cargo xtask bench --update`: baselines are tied to the
   emulator version), and run the suite on the **released** build for this
   platform too (`RETROPANE_QEMU=release cargo xtask emu`: on Windows that
   is the native build contributors download, which the local WSL build and
   Linux CI don't cover; item 61 hid there for two releases).
3. Add the row here either way.
