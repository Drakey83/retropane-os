# The emulator and the real hardware

The emulator (`Drakey83/retropane-qemu`, a QEMU fork with X51v models) is
only useful while it behaves like the device. **Rule:** every fact learned
on the real X51v that a model could reproduce goes into the fork, with a
test in `cargo xtask emu` that fails without it; what can't be modelled is
listed here with the reason, so nobody trusts the emulator for it. Each row
names the finding, where it is written up, and the emulator's state.

| Finding (date) | Written up | Emulator |
|---|---|---|
| UDC: software sends the status IN for host-to-device control transfers; HXOE must stay set; one packet in flight; only the active interface's endpoints work; IN `UDCCSR` bit 6 = "not full" (2026-10-11) | `udc.md` | Modelled (rp-v0.7.0, `hw/misc/pxa27x-udc.c`), tested by the loader-over-USB boot |
| MMC: the CMD12 ending a multi-block **write** needs `CMDAT[10]` stop-transmission, else the controller never issues it (2026-10-11) | `sd.md` | Modelled (rp-v0.8.0): the model issues a stop command once the transfer is finished; upstream never issued it. Tested by the file-to-card boot |
| SD card: still busy programming after the CMD12 that stops a write; the next command gets no response unless the driver polls CMD13 (2026-10-11) | `sd.md` | Modelled (rp-v0.8.0): the emulated card answers the first CMD13 polls after a write with the `prg` state and "not ready for data", so a driver without the poll fails in CI as on the device (checked: with the poll removed, the suite reports the device's exact reply, `timeout on CMD24 stat 0x102`) |
| USB hosts wait 10 ms after a bus reset before the first request (USB 2.0 reset recovery) (2026-10-12, specification; found as an emulator race) | `udc.md` | Modelled (rp-v0.9.0). The driver also keeps a SETUP that arrives before it handles the reset, tested in `pxa-udc` with a mutation that makes it fail |
| A composite device's functions are told apart by interface class in the configuration descriptor; storage works with no program on the serial port (2026-10-12, how Windows binds IAD composites) | ADR-0014 | Modelled (rp-v0.9.0): descriptor-driven routing, Get Max LUN, the drive bridged to a second chardev. Tested by the drive boot |
| SD card: one block too slow for a multi-block read; the timed-out CMD18 leaves the card sending, so the stopping CMD12 is illegal and ILLEGAL_COMMAND shows in the next response (2026-10-12) | `sd.md` | Modelled (rp-v0.9.2): `pxa2xx-mmci.slow-address` times out a multi-block read at that block and stops the card; the drive test's 1 MiB read crosses it and must return the image's bytes. Not modelled: single reads of it failing too once provoked (the card's internal state) |
| CF slot power is two CPLD bits (`0x16` bit 1, `0x10` bit 12), its RESET is CPLD `0x18` bit 1, GPIO84 = slot powered; Windows Mobile hands over with the slot off or powering down, so a card works for a moment and then reads 0 (2026-10-12; was first read as "inherited state") | `cf.md` | Modelled (rp-v0.11.0, item 62 (a)): the slot starts unpowered; the card answers only while both power bits are set and RESET (`0x18` bit 1) is clear, reads 0 otherwise; GPIO84 = card in and powered (stays high in reset, as measured); power-up and the release of RESET put the card in its power-on state. The CF check runs `cf soft` (no power sequence) first and needs it to fail, then `cf`; mutants with the loader's power-on or backlight enable removed fail it. The fork's GPIO36 reset model is gone. Card removal (rp-v0.11.1): `qom-set /machine/peripheral/cfslot pressed true` pulls the card out (GPIO13 high, CPLD `0x04` bit 1 set), `false` puts it back; the CF check needs the loader to have switched the slot off by then (GPIO84 stays low) and `cf` to take the card again. Not modelled: the hand-over's brief residual power (a card working for ~120 ms before going dark: cause unknown), busy times after power-up or reset |
| The CPLD's registers don't read back; the backlight enable is `0x18` bit 2 (2026-10-12) | `cpld.md` | Modelled (rp-v0.11.0): writes go to latches that never read back; reads return the status values measured with Windows Mobile's state (`00=0048 04=00a0 06=0002 14=0002`, `0x04` bit 1 set with no CF card; `0x1E` the LCD type while latch bit 3 is set). The latches start as Windows Mobile hands over (backlight enable on, CF slot off); `0x18` bit 2 clear blanks the screen (the picture kept), readable as `qom-get /machine/peripheral/mbx2700g backlight`; the CF check fails if the loader's CPLD writes switch it off. Not modelled: the other bits' effects (SD power, Wi-Fi, audio... `cpld.md` guesses) and what else Windows Mobile leaves on |
| CPLD reads as Windows Mobile leaves them: `00=0048 04=00a0 06=0002 14=0002` (2026-10-12) | `cpld.md` | Modelled (rp-v0.11.0) as status inputs (above), not written values |
| PC Card socket timings as Windows Mobile leaves them (MCMEM/MCATT/MCIO = 0x00020508/0x00020E08/0x00020510, both sockets) (2026-10-12) | `cf.md` | Not modelled yet: the X51v machine has no CF socket model; added with the CF driver |
| SD card detect GPIO12 (low = in) and write-protect GPIO27 (high = locked) (2026-10-12) | `sd.md` | Modelled (rp-v0.9.3): wired from the MMC model; `pxa2xx-mmci.locked=on` sets the lock, the card stays writable as a real one does |
| PWM0 drives the backlight; WM leaves period 0xD7, duty 0x89 (2026-10-11) | `backlight.md` | Modelled (rp-v0.9.4): registers stored, readable via `qom-get /machine/peripheral/pwm dcr0`; no waveform. Cold start has no period: the driver sets WM's |
| Power button on GPIO0, resting at 0, both edges watched by WM (2026-10-11 probe) | `README.md` | Modelled (rp-v0.9.5): `x51v-button`, pressed via `qom-set /machine/peripheral/power pressed true`; pressed = 1 is the model's guess (the loader doesn't depend on it) |
| PXA27x DMA serves peripheral requests asynchronously; a descriptor without STOP chains to the next; the MMC receive request follows the FIFO's contents (2026-10-12, PXA27x manual; found as emulator faults) | `sd.md` | Modelled (rp-v0.9.6): upstream ran the DMA synchronously inside the MMC's register access (QEMU blocks the re-entrant FIFO read), stopped after the first descriptor, and left the receive request raised after the FIFO emptied, so the next transfer's DMA read nothing before its command. Requests are now served from a virtual-clock timer (deterministic under `-icount`). The bench's `sd_multi_block_matches` check and the loader's DMA self-test fail without it |
| CompactFlash: socket 1, card detect on GPIO13 (low = card in) (2026-10-12) | `cf.md` | Modelled (rp-v0.9.7): QEMU's PC Card socket with its CF card model on `-drive if=ide` (CIS, memory mode, ATA); an empty slot reads high. READY (GPIO84) modelled (rp-v0.10.1), now slot power from the CPLD (rp-v0.11.0, row above). Not modelled: busy times after reset or a command, the card's interrupt, the socket timing registers' effect |
| Audio: WM8750 on the standard I2C bus, fed by the PXA27x I2S (2026-10-12, AxDroid board code) | `audio.md` | Modelled (rp-v0.9.8): QEMU's WM8750 at 0x1A on the PXA I2C bus and its I2S model; `-machine audiodev=` picks the output (the tone test records a wav and measures the pitch). The codec's real address (0x1A or 0x1B) is unknown, so the driver tries both. Not modelled: the speaker amplifier (GPIO82, CPLD 0x14). Headphone jack on GPIO83 modelled (rp-v0.9.9) as a switch, high = plugged (the assumed polarity) |
| 2700G plane composition: video plane (UYVY, planar 4:2:0), layer slots, blend modes, `BGCOLOR`, ARGB4444; `VOVRCLK` gates the video plane (2026-10-12, mbxfb (B); confirmed on the device by `rp-blend`: alpha direction, 4:2:0 layout, colour conversion by eye) | `2700g.md` "Plane composition" | Modelled (rp-v0.10.0), with the spec's mixing arithmetic exactly; `rp-blend`'s three stages must match the Rust reference pixel for pixel. Not modelled: colour keys, gamma, the scaler (1:1 only), the cursor, the chip hang when `VSCTRL` goes planar before the chroma bases are set |
| Windows Mobile's software reboot: GPIO99 high (after `PCFR` GPR_EN, GPIO15 low, CPLD `0x08` bit 1) resets the board without Dell's factory prompt (2026-10-13, from the kernel; not yet on the device) | `README.md` "Software reset" | Not modelled until the device confirms it: GPIO99 does nothing in the emulator, and the backlight check needs `reboot wm` to report "no reset" and the loader to carry on. Once confirmed: GPIO99 high resets the machine |
| Touch: Windows Mobile leaves GPIO24 (the TSC2046's chip select) as SSP1's frame signal, function 2 (`GAFR0U = 0x001A851A`); used as a GPIO without switching it to function 0, chip select does nothing and every reading is 0 (all taps at the top left) (2026-10-13, `rp-today` on the device) | `touch.md` | Not modelled yet: the fork's GPIO block has no pin functions, so its TSC2046 answers whatever GPIO24's function. To model: start with WM's `GAFR` values and answer only while GPIO24 is a plain GPIO driven low; `rp-today` and `rp-hello` would fail without `set_function` |
| SD card: 3.85 ms per single-block read (per-command cost dominates) (2026-10-11) | `sd.md`, `perf.md` | Not modelled: the emulator's benchmarks are deterministic instruction counts (ADR-0007), not card latencies. Real-card numbers live in `perf.md` |
| XScale: enabling or disabling the MMU, the CPWAIT and the next instructions must share one 32-byte cache line (2026-10-11) | `README.md` (first facts) | Not modellable: QEMU has no cache-line pipeline effects. The HAL's aligned assembly is the only guard; keep the device run as the test |
| Windows Mobile leaves DMA channels and the UDC running at handoff; the 2700G needs ~0.5 s to settle (2026-10-11) | `README.md`, `2700g.md` | Not modelled: the emulator starts from reset, not from Windows Mobile's state. `_start` stops DMA/UDC on both |
| Windows Mobile leaves the graphics plane at offset 0 of the 2700G's memory (`GSCTRL` 0x3C0EFA7F, `GSCADR` 0x80000000, `GSADR` 0x0EC00000), not at the conventional 0x60000 (2026-10-11) | `2700g.md` "Measured on a real X51v" | Not modelled in the fork: it starts from reset (no plane), and QEMU's `-device loader` register presets are cleared by the 2700G's own reset. Stood in for by `rp-crash`, which moves the plane to offset 0 itself before it crashes: the crash check (`cargo xtask emu-crash`) fails if an image's crash box is drawn at 0x60000 instead of on the plane on screen (2026-10-12). A fork option starting the 2700G in WM's display state would also cover the loader's own start |
| The X51v's D+ pull-up is a fixed resistor: the PC never sees the device disconnect (2026-10-11) | `udc.md`, ADR-0012 | Modelled in spirit: the emulated host re-enumerates when the loader re-enables the UDC; the Windows device-restart task exists only for the real cable |

## How to add a row

1. Record the fact in the block's spec (`docs/hw/<block>.md`) with its
   evidence, as always (`CLEANROOM.md`).
2. If a model can reproduce it: change the fork, add or extend an emulator
   boot in `xtask/src/emu.rs` that fails without the change, tag a release
   (`rp-vX.Y.0`), bump `QEMU_RELEASE` in `xtask/src/emu.rs`, re-record the
   bench baseline (`cargo xtask bench --update`: baselines are tied to the
   emulator version), and run the suite on the **released** build for this
   platform too (`RETROPANE_QEMU=release cargo xtask emu`: on Windows that
   is the native build contributors download, which the local WSL build and
   Linux CI don't cover; item 61 hid there for two releases).
3. Add the row here either way.
